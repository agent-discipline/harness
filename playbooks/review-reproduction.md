# playbook: 리뷰 지적의 재현과 영향 등급

> 트리거: 리뷰어 프롬프트를 쓸 때(`review.md` §1 ①) · 지적을 종합할 때(②) — 코드 동작 지적을 채택하기 전, 그리고 남기는 결함을 보고할 때. 리뷰어 출력 칸과 ledger `repro` 값의 정본은 `review.md`(§1 ① · §2), 가르는 순서는 `review-triage.md` — 이 문서는 메인이 재현하고 등급 · 보고 · 반복 유형을 다루는 절차다.
> 왜: 리뷰어는 읽기 전용 미러에서 코드를 읽기만 한다 — 지적의 실패 시나리오는 추론이다. 2026-11-21 실측(seat-reservation-lab ADR-018 기본값 교체): 메인도 코드 읽기로만 채택해 같은 유형을 네 번 고친 뒤에야 실행했고(5건 중 재현 3 · 잠재 1 · 테스트 준비 오류 1), 남은 계약 결함을 '크리티컬하지 않다'고 보고해 사용자가 정정했다. `docs/plans/2026-11-21/review-reproduction-impact/`.

## 1. 출력 칸이 빠진 지적

- 재현이나 등급이 빠진 지적은 open question이다(`review.md` §2 자격 ⑤). 원문에 시나리오와 근거(file:line)가 있으면 메인이 확인해 다시 가른다 — 재현은 §2로 직접 만들고 등급은 원문으로 정해, ledger에 '(메인 보충)'이라고 적는다. 시나리오도 없으면 open question으로 두고 다음 루프에 리뷰어에게 다시 묻거나, 근거가 없다는 확인으로 기각한다.

## 2. 메인이 채택 전에 하는 것

- **코드 동작 지적의 채택 조건은 셋 중 하나다**: ① 실행 재현 ② 예외 셋 ③ `잠재`로 적은 뒤 `review-triage.md` (3)(4)를 통과. 빈 `repro`로 채택하지 않는다.
- **실행 재현은 리뷰한 코드에서 한다** — log packet 행의 '리뷰한 SHA'(packet을 만들기 전에 커밋한 상태 — `review.md` ⓪). task base SHA가 아니다(이번 변경이 만든 결함은 거기에 없다). 그 SHA로 repo 밖(scratchpad)에 임시 worktree를 만들어 돌리고, 판정 뒤 이 절차에서 만든 worktree만 정리한다. 재현에 쓴 테스트는 고칠 때 수정 검증 테스트로 옮긴다(`review.md` ④). task base에서 통과하는지는 (3) '이번 변경이 만들었나'의 보조 증거로만 쓴다.
- 리뷰어의 재현 방법이 맞지 않거나 없으면 메인이 테스트를 새로 쓴다(실측: 빈 DB에서 Flyway를 끈 기동은 스키마 검증이 먼저 실패 — 준비를 고친 뒤 판정). 실패가 지적한 이유로 난 것인지 메시지로 확인한다.
- 지적이 많거나 실행이 길면 **검증 워커**에게 맡긴다 — 리뷰어가 아닌 새 워커. 브리핑(core §5 다섯 요소)에 재현 방법 · 기대 실패 · 리뷰한 SHA를 넣고 메인의 판정은 넣지 않는다. 결과는 메인이 ledger에 적는다.
- **예외 셋**은 실행하지 않고 `코드로만 확인 — 이유`: 문서 · 주석 · 테스트 공백(그 테스트가 통과한 채로 결함이 들어올 수 있는가 — `review-triage.md` (2)) · 명세 위반이 코드만으로 자명한 것. 실행 효력이 있는 정책 문서는 읽기 시험을 돌렸으면 `실행 — 읽기 시험`. 설계 문서 리뷰는 `해당 없음 — 설계 문서`.
- 돌려도 통과하면 **`잠재`**(순서 · 시각 · 환경에 따라 나는 결함)다 — 리뷰한 SHA · 시도 · 결과를 적는다. 재현 테스트 통과는 (2)의 '실측으로 반증'이 아니다. (3)(4)로 가른다.
- 메인이 재현 수단을 만들 수 없으면(환경이 없는 등) `잠재`로 적지 않는다 — open question으로 두고 그 이유와 확인 방법을 적는다(`review-triage.md` §2 '아직 못 가름'). 실행 없이 채택으로 가는 길을 만들지 않기 위해서다.
- 실행하지 않고 기각이나 후보로 간 지적은 `미실행 — 갈래와 이유`.

## 3. 잠재 결함을 고칠 때

- 수정 검증 테스트는 재현 조건(빈 생성 순서 · 시각)에 기대지 않고 계약을 직접 확인한다. 실측: 빈 순서를 고정하는 수정(@DependsOn)을 '지금 순서에서 통과하는 테스트'로 확인했다가 재점검에서 그 테스트가 수정을 검증하지 못한다는 지적을 받았다 — 계약(어느 검사가 먼저 거부해도 안내가 있다)을 직접 만족시키는 쪽으로 바꾸고 순서 고정은 뺐다.

## 4. 영향 등급 — 갈래가 아니라 순서와 노력을 정한다

| 등급 | 뜻 |
|---|---|
| 데이터 | 손실 · 오염 · 조용히 틀린 값 |
| 보안 | 권한 · 노출 · 공격 경로 |
| 가용성 | 멈춤 · 기동 불가 · 자원 고갈 |
| 계약 | 응답 · 설정 · 안내가 약속(명세 · 메시지)과 다름 |
| 검증 | 테스트 공백 · 그린 위장 |
| 문서 | 문서 · 주석의 표현 · 기록(문서가 틀린 안내를 해도 동작이 약속대로면 문서) |

- **등급은 고칠지를 정하지 않는다** — 고칠지는 `review-triage.md` §1의 (1)~(4)다. 등급은 재현에 들일 노력, 보고 순서, 같은 S/A/B 안의 순서, §6 반복 유형 판단에 쓴다. 계약 등급은 B(표현 · 기록만)가 아니다.

## 5. 보고 규칙

- **결함 여부와 등급을 한 판정으로 섞지 않는다.** 남기는 결함은 갈래와 그 근거((3) 원래 있던 것 등)로 적는다. '크리티컬하지 않으니 남겨도 된다'고 말하지 않는다 — 계약 등급도 동작이 약속과 다르면 결함이다(실측: 사용자 "다 수정해야되는 이슈들이잖아 이건 동작이나 계약에 문제가 있다는거 아니야?"). 사용자가 이 작업에서 고치기를 원하면 `review-triage.md` §2(후보를 같은 작업에 더할 때)를 따른다.
- 실행으로 확인하지 않은 판정은 보고에도 '코드로만 확인' · '잠재'라고 쓴다.

## 6. 같은 유형이 다시 나올 때 (정본 — `review-triage.md` §4는 여기를 가리킨다)

- **같은 유형** = 같은 명세 조항이나 계약을 다른 경로에서 어긴 것(실측: '첫 거부 메시지에 안내 없음'이 보상 검사 · target 계획 검사 · yml 주석 · 검사 순서에서 네 번).
- 같은 작업 안에서 같은 유형이 두 번째로 채택되면 하나씩 막지 않고 원인이 된 구조를 확인한다. 구조 수정이 목표 안이면 구조로 고치고(목표 안인지 = `review-triage.md` (4)의 목표 · 불변식으로 읽는다), 밖이면 후보로 적고 보고에 그 구조를 원인으로 적는다(실측: 기동 검사가 먼저 걸린 하나만 보고하는 구조 → 별도 작업으로).
- core §3 정지 규칙(같은 결함을 2회+ 고쳐도 또 깨짐)은 같은 결함의 재발이고, 이 줄은 같은 유형의 다른 결함이다 — 둘 다 해당하면 core §3이 먼저다.
- 명세 단계에서는 `templates/requirement-spec.md` ② 칸의 '가로지르는 계약'이 같은 일을 앞에서 막는다.
