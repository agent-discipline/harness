# playbook: 리뷰 지적의 재현과 영향 등급

> 트리거: 리뷰 지적을 종합할 때(`review.md` §1 ②) — 코드 동작 지적을 채택하기 전, 그리고 남기는 결함을 보고할 때. 가르는 순서는 `review-triage.md`가 정본이고, 이 문서는 그 (2)의 재현 절차와 등급 · 보고 규칙만 다룬다.
> 왜: 리뷰어는 읽기 전용 미러에서 코드를 읽기만 한다 — 지적의 실패 시나리오는 추론이다. 2026-11-21 실측(seat-reservation-lab ADR-018 기본값 교체): 메인도 코드 읽기로만 채택해 같은 유형을 네 번 고친 뒤에야 실행했고(5건 중 재현 3 · 잠재 1 · 테스트 준비 오류 1), 남은 계약 결함을 '크리티컬하지 않다'고 보고해 사용자가 정정했다. `docs/plans/2026-11-21/review-reproduction-impact/`.

## 1. 리뷰어가 내는 것

- 지적마다 실패 시나리오 + **재현**(수정 전 코드에서 실패할 테스트 · 명령, 없으면 '재현 불가 — 이유') + **영향 등급**(§4). 빠지면 finding이 아니라 open question이다(`review.md` §2 자격 조건 ⑤).
- 리뷰어는 실행하지 않는다(미러 read-only) — 재현 방법을 내고, 실행은 메인이 한다.

## 2. 메인이 채택 전에 하는 것

- **코드 동작 지적은 실행 재현이 채택의 조건이다.** 수정 전 코드(task base SHA의 임시 worktree)에서 재현 방법을 돌려 실패를 보고, ledger `repro`에 `실행 — 명령 · 결과`로 적는다. 리뷰어의 재현 방법이 맞지 않으면 메인이 테스트를 새로 쓴다(실측: 빈 DB에서 Flyway를 끈 기동은 스키마 검증이 먼저 실패 — 준비를 고친 뒤 판정).
- 지적이 많거나 실행이 길면 **검증 워커**에게 맡긴다 — 리뷰어가 아닌 새 워커, 재현 방법과 base SHA만 받는다. 결과는 메인이 ledger에 적는다.
- **예외 셋**은 실행하지 않고 `코드로만 확인 — 이유`로 적는다: 문서 · 주석 · 테스트 공백(그 테스트가 통과한 채로 결함이 들어올 수 있는가 — `review-triage.md` (2)) · 명세 위반이 코드만으로 자명한 것. 산출물이 설계 문서인 리뷰는 `해당 없음 — 설계 문서`.
- 돌려도 통과하면 **`잠재`**(순서 · 시각 · 환경에 따라 나는 결함)다 — 기각 사유가 아니다. 시도와 결과를 적고 `review-triage.md` (3)(4)로 가른다.

## 3. 잠재 결함을 고칠 때

- 수정 검증 테스트는 재현 조건(빈 생성 순서 · 시각)에 기대지 않고 계약을 직접 확인한다. 실측: 빈 순서를 고정하는 수정(@DependsOn)을 '지금 순서에서 통과하는 테스트'로 확인했다가 재점검에서 그 테스트가 수정을 검증하지 못한다는 지적을 받았다 — 계약(어느 검사가 먼저 거부해도 안내가 있다)을 직접 만족시키는 쪽으로 바꾸고 순서 고정은 뺐다.

## 4. 영향 등급 — 갈래가 아니라 순서와 노력을 정한다

| 등급 | 뜻 |
|---|---|
| 데이터 | 손실 · 오염 · 조용히 틀린 값 |
| 보안 | 권한 · 노출 · 공격 경로 |
| 가용성 | 멈춤 · 기동 불가 · 자원 고갈 |
| 계약 | 응답 · 설정 · 안내가 약속(명세 · 문서 · 메시지)과 다름 |
| 검증 | 테스트 공백 · 그린 위장 |
| 문서 | 표현 · 기록 |

- **등급은 고칠지를 정하지 않는다** — 고칠지는 `review-triage.md` §1의 (1)~(4)다. 등급은 후보의 S/A/B, 재현에 들일 노력, 보고 순서에 쓴다.

## 5. 보고 규칙

- **결함 여부와 등급을 한 판정으로 섞지 않는다.** 남기는 결함은 갈래와 그 근거((3) 원래 있던 것 등)로 말하고, 이 작업에서 고칠지 사용자가 고르게 한다. '크리티컬하지 않으니 남겨도 된다'고 말하지 않는다 — 계약 등급도 동작이 약속과 다르면 결함이다(실측: 사용자 "다 수정해야되는 이슈들이잖아 이건 동작이나 계약에 문제가 있다는거 아니야?").
- 실행으로 확인하지 않은 판정은 보고에도 '코드로만 확인'이라고 쓴다.

## 6. 같은 유형이 다시 나올 때

- 같은 유형의 결함이 두 번째로 채택되면 하나씩 막지 않고 원인이 된 구조를 사용자에게 묻는다(core §3 정지 규칙의 리뷰판 — 실측: '첫 거부 메시지에 안내 없음'이 경로만 바꿔 네 번 나왔고, 원인은 명세의 계약 범위가 열려 있던 것과 검사마다 자기 키만 안내하는 구조였다).
- 명세 단계에서는 `templates/requirement-spec.md` ② 칸의 '가로지르는 계약'이 같은 일을 앞에서 막는다.
