# 웹과 서버의 통신 분기표

브라우저(웹 화면, 관리자 화면)와 우리 서버가 어떻게 통신할지 정할 때 읽는다. 우리가 만든 서비스 사이는 [service-communication.md](service-communication.md), 우리가 배포하지 않는 시스템이 우리를 부르는 경우는 그 문서 3절, 브라우저와 서버 사이의 암호화(https, wss)는 그 문서 5절이 정한다. 모바일 앱, 파일 전송, 미디어 스트리밍은 이 문서가 정하지 않는다(끝의 "아직 줄이 없는 것"). 줄의 형식과 근거의 종류, 줄이 없거나 부딪힐 때의 절차, 전환 기준은 [ROUTING.md](ROUTING.md)에 있다.

- **근거**: 이 문서의 근거는 모두 사용자 판단과 일반 지식(표준과 공식 문서)이다. 웹 통신을 직접 잰 실측은 없다. 크기가 있는 얻는 것과 내주는 것(연결 수별 메모리, 다시 붙기까지의 시간, 왕복 횟수, 지연, 서버의 조회 횟수, 응답 크기)에는 "잴 것: 웹 통신 실험의 ○○"를 붙였고, 방향조차 문서로 받칠 수 없는 것은 "방향도 잴 것"으로 적었다. 브라우저나 표준, 제품이 정한 고정 한도와 기본값은 "브라우저의 한도", "제품의 기본값"으로 밝히고 출처만 적었다. 웹 통신 실험은 다음 작업이다.
- **낱말**: 운영하는 방식 — 우리 서버가 클라이언트(브라우저, 모바일 앱, 그 밖의 클라이언트)에 이미 열어 운영하고 있는 방식(HTTP + JSON, GraphQL, SSE, WebSocket). 모바일 앱에 연 GraphQL, 다른 화면에서 운영하는 SSE나 WebSocket도 여기에 들고, 이 화면이 이미 연 연결(함께 편집의 WebSocket, 알림의 SSE)도 든다. 운영하는 방식과 이미 연 연결은 이 설계를 시작하기 전에 이미 열어 운영하던 것이고, 이번 설계에서 방금 고른 방식은 들지 않는다(처음 고르는 설계에서는 호출마다 처음 고를 때의 줄에서 고른다). "운영하는 방식이 없다(처음 고른다)"는 우리 서버가 어느 클라이언트에도 연 방식이 하나도 없을 때다. 따로 만드는 클라이언트 — 따로 만들고 따로 배포하는 화면의 묶음(웹앱, 모바일 앱, 관리자 화면). 한 웹앱 안의 목록, 상세, 대시보드는 클라이언트 하나다. 다시 붙기 — 끊긴 연결을 다시 여는 것. 이어 받기 — 끊긴 동안 놓친 메시지를 다시 붙은 뒤 받는 것. SSE(server-sent events) — 브라우저가 EventSource로 열고 서버가 이벤트를 이어 보내는 HTTP 응답.

## 1. 어느 방식을 쓰나

첫 줄은 운영하는 방식이 있을 때, HTTP + JSON, GraphQL, SSE, WebSocket 줄은 운영하는 방식이 없어 처음 고를 때 쓴다. 운영하는 방식이 있으면 첫 줄만 보고, 첫 줄에 들지 않으면 처음 고를 때의 줄로 가지 않고 아래 묻는 경우의 첫째 항목대로 한다. 다만 GraphQL로 묻는 화면에 실시간 값이 필요하면, 운영하는 GraphQL에 그 값을 보내는 subscription이 이미 있을 때는 첫 줄(그 subscription을 쓴다)이고, 없을 때는 첫 줄과 처음 고를 때의 줄을 보기 전에 묻는 경우의 넷째 항목대로 묻는다. 그 subscription이 없으면 운영하는 SSE나 이 화면이 이미 연 연결이 있어도 같다(GraphQL로 묻는 것과 실시간 값을 받는 것이 두 줄에 걸치기 때문이다). gRPC 줄은 어느 경우에나 함께 걸리고, 브라우저 쪽의 방식은 다른 줄로 고르므로 두 줄에 걸친 것으로 보지 않는다. 한 기능이 두 호출로 나뉘는 것(진행률은 SSE로, 결과는 HTTP 요청으로)도 호출마다 따로 고르는 것이라 걸침이 아니다(GraphQL로 묻는 화면의 실시간 값은, 그 값을 보내는 subscription이 운영하는 GraphQL에 없으면 이 말과 상관없이 넷째 항목이다). 어느 줄을 고르든 고른 방식이 필요한 기능을 모두 채우는지 2절 기능 표에서 본다. 파일 전송과 미디어 스트리밍은 운영하는 방식으로 보낼 수 있더라도 어느 줄에도 들지 않는다(끝의 "아직 줄이 없는 것").

아래 경우에는 고르지 않고 사용자에게 묻는다. 넷째는 그 값을 보내는 subscription이 운영하는 GraphQL에 없을 때 첫 줄과 처음 고를 때의 줄보다 앞서고(이미 있으면 첫 줄이다), 다섯째는 줄을 고른 뒤 인증을 싣는 방법을 묻는다. 운영하는 방식이 있을 때 묻는 선택지에는 지금 것으로 채우는 안이 들어간다.

- 운영하는 방식이 이 화면에 필요한 것을 채우지 못한다(첫 줄에 들지 않는다). 예: HTTP + JSON만 운영하는데 서버가 먼저 보내야 한다. 메인이 새 방식을 고르지 않는다. `ROUTING.md` "줄을 따를 때"의 전환 기준대로 가능한 선택지를 모두(지금 것으로 채우는 안과 작은 실험으로 견준 뒤 정하는 안 포함. 지금 것으로 채우는 안의 예: HTTP + JSON으로 일정 간격마다 다시 묻는다) 얻는 것과 내주는 것과 함께 보이고 승인받는다. 선택지마다의 얻는 것과 내주는 것은 처음 고를 때의 줄과 2절 표에서 가져온다. 브라우저도 가끔 보내는 화면(채팅)이면 선택지는 셋째 항목의 것이다.
- 운영하는 방식 둘 이상이 첫 줄에 들고, 이 화면이 이미 연 연결로도 정할 수 없다.
- 서버가 보내는 값에 대해 브라우저도 보내는데 WebSocket 줄(두 쪽이 내내 주고받는다)에 드는지 구분할 수 없다. 운영하는 방식이 없을 때(처음 고른다)와, 운영하는 방식이 채우지 못해 첫째 항목에서 올 때 모두 쓴다. 예: 채팅의 보내기, 좋아요처럼 브라우저가 가끔 보낸다. 메인이 먼저 보는 안은 SSE + 보통의 HTTP 요청이지만 고르지 않는다. 선택지는 SSE + HTTP 요청(다시 붙기를 브라우저가 해 주고, 브라우저가 보내는 것은 SSE와 따로 된 요청이다) / WebSocket(한 연결로 주고받고, 다시 붙기와 이어 받기를 직접 만든다) / 운영하는 방식이 있으면 지금 것으로 채운다(예: HTTP + JSON으로 일정 간격마다 다시 묻는다 — 값이 늦게 닿고 요청이 는다, 크기는 잴 것) / 작은 실험으로 견준 뒤 정한다(안마다 다시 붙기까지의 시간, 놓친 메시지 수, 연결 수별 서버 메모리, 다시 묻는 안이면 값이 늦게 닿는 시간과 요청 수를 잰다. 드는 시간은 물을 때 적는다)이고, 대가는 SSE 줄과 WebSocket 줄에 있다.
- GraphQL로 묻는 화면에 실시간 값이 필요한데, 운영하는 GraphQL에 그 값을 보내는 subscription이 없다. 이 항목은 첫 줄과 처음 고를 때의 줄보다 앞선다(그 값을 보내는 subscription이 이미 있으면 이 항목이 아니라 첫 줄이다). 운영하는 SSE나 이 화면이 이미 연 연결이 있어도, 처음 고를 때 GraphQL 줄과 SSE 줄이 함께 걸려도 묻는다. subscription은 그 자체가 전송 방식이 아니라 보통 WebSocket이나 SSE 위에서 돈다([Subscriptions](https://graphql.org/learn/subscriptions/)). 선택지는 스키마 안의 subscription으로 받는다(전송은 SSE나 WebSocket을 다시 고르고, 2절 장단점 표의 subscription 대가를 치른다) / 스키마 밖의 따로 된 SSE로 받는다(운영하는 SSE가 있으면 그것으로. 그 값만 GraphQL 밖의 계약이 된다) / 운영하는 방식이 있으면 지금 것으로 채운다(예: GraphQL query로 일정 간격마다 다시 묻는다 — 값이 늦게 닿고 요청이 는다, 크기는 잴 것) / 작은 실험으로 견준 뒤 정한다(안마다 값이 닿기까지의 지연, 요청 수, 연결 수별 서버 메모리를 잰다. 드는 시간은 물을 때 적는다)다.
- 헤더로 인증을 실어야 하는데 고른 줄이나 쓰려는 연결이 SSE나 WebSocket이다. 선택지는 같은 출처에 두고 쿠키로 인증한다(EventSource는 `withCredentials`를 켜면 다른 출처의 요청에도 자격 증명을 싣고, WebSocket 서버는 쿠키 같은 HTTP 서버의 인증 수단을 쓸 수 있다) / EventSource 대신 fetch로 SSE 응답을 스트림으로 읽는다(헤더를 싣는 대신, EventSource가 해 주던 다시 붙기와 `Last-Event-ID`를 화면 코드가 직접 만든다) / 토큰을 URL에 싣는다(URL에 실은 토큰은 로그에 남을 가능성이 커서, RFC 6750은 `Authorization` 헤더나 본문으로 보낼 수 없을 때만 쓰라고 적고, 브라우저 기록과 웹 서버 로그에서 토큰을 훔칠 수 있다고 적는다 — [RFC 6750 2.3](https://www.rfc-editor.org/rfc/rfc6750#section-2.3), [5.3](https://www.rfc-editor.org/rfc/rfc6750#section-5.3))이다. 로그인이 만료되어 다시 붙을 때 401이 오면 EventSource가 멈추므로, 화면이 이것을 알아채고 다시 여는 방법도 함께 정한다.
- 고른 방식이 2절 기능 표에서 조건부의 조건을 채우지 못하거나, 조건끼리 부딪히거나, "확인하지 않았다"에 걸린다.
- 브라우저가 쓸 기능이 gRPC 서비스에만 있는데, 브라우저가 부를 서버를 새로 둬야 하거나 그 gRPC 서비스가 HTTP + JSON도 함께 열어야 할 것 같다(gRPC 줄). 구성 요소를 더하는 것이라 메인이 고르지 않는다. 전환 기준대로 선택지는 브라우저가 부를 서버를 새로 둔다(운영할 서버가 하나 늘고, 그 서버를 거치는 만큼 지연이 는다 — 크기는 잴 것) / 그 gRPC 서비스가 HTTP + JSON도 함께 연다(한 서비스가 HTTP와 gRPC 두 가지를 함께 연다) / 작은 실험으로 견준 뒤 정한다(두 안에서 브라우저가 응답을 받기까지의 지연을 잰다. 드는 시간은 물을 때 적는다)이고, 메인이 권하는 안과 근거를 밝혀 승인받는다.

## 2. 방식별 기능과 장단점

선택이 없는 사실만 모은 두 표다. 확인한 날: 2026-11-22(두 표 모두).

기능 표는 고른 방식이나 운영하는 방식이 필요한 기능을 채우는지 볼 때 쓴다. 칸의 값은 지원, 조건부(조건을 적었다), 확인하지 않았다(지원하지 않는다는 뜻이 아니다), 안 된다(출처가 그렇게 적었다), 해당 없음(그 방식에서는 물음이 성립하지 않는다) 다섯이다.

| 방식 | 서버가 먼저 보내기 | 브라우저가 그 연결로 계속 보내기 | 다시 붙기와 이어 받기 | HTTP 캐시 | 인증 헤더 |
|---|---|---|---|---|---|
| HTTP + JSON | 해당 없음: 서버는 요청에 응답을 보낸다([RFC 9110 3.3](https://www.rfc-editor.org/rfc/rfc9110#section-3.3)) | 해당 없음: 요청마다 따로 보낸다([RFC 9110 3.3](https://www.rfc-editor.org/rfc/rfc9110#section-3.3)) | 해당 없음: 요청마다 새로 보낸다([RFC 9110 3.3](https://www.rfc-editor.org/rfc/rfc9110#section-3.3)) | 지원: 흔히 쓰는 HTTP 캐시는 GET 응답을 URI를 키로 둔다([RFC 9111](https://www.rfc-editor.org/rfc/rfc9111)). 공유 캐시는 `Authorization`이 실린 요청의 응답을 허락하는 지시가 있을 때만 다시 쓴다([RFC 9111 3.5](https://www.rfc-editor.org/rfc/rfc9111#section-3.5), [MDN HTTP caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)) | 지원: fetch의 `headers`([MDN Using Fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)). 다른 출처면 preflight가 먼저 간다([MDN CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)) |
| GraphQL | 조건부: subscription. 전송은 GraphQL이 정하지 않고 보통 WebSocket이나 SSE를 쓴다([Subscriptions](https://graphql.org/learn/subscriptions/)) — 그 방식의 행 | 확인하지 않았다 | 조건부: subscription은 끊기면 클라이언트 라이브러리가 다시 구독하는 로직이 필요하다([Subscriptions](https://graphql.org/learn/subscriptions/)). 이어 받기는 확인하지 않았다 | 조건부: 기본은 한 엔드포인트의 POST다([Serving over HTTP](https://graphql.org/learn/serving-over-http/), POST 응답의 캐시 조건은 [RFC 9110 9.3.3](https://www.rfc-editor.org/rfc/rfc9110#section-9.3.3)). query를 GET으로 받고 캐시 헤더를 주면 HTTP 캐시와 CDN을 쓰지만, URL 길이 한도 때문에 persisted query가 필요할 수 있다([Performance](https://graphql.org/learn/performance/)) | 지원: query와 mutation은 HTTP POST라([Serving over HTTP](https://graphql.org/learn/serving-over-http/)) fetch의 `headers`로 싣는다([MDN Using Fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)). subscription은 그 전송 방식의 행 |
| SSE | 지원([MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)) | 안 된다: 서버에서 브라우저로만 가는 단방향이다([MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)) | 조건부: 브라우저 — 다시 붙고 `Last-Event-ID`를 보낸다. 서버 — 그 id 뒤의 것을 보내는 것은 서버 코드가 만든다. 응답이 200이 아니거나 `Content-Type`이 `text/event-stream`이 아니면 다시 붙지 않는다([WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)) | 안 된다: EventSource의 요청은 cache mode가 `no-store`다([WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)) | 조건부: 생성자가 받는 것은 URL과 `withCredentials`뿐이라 헤더를 넘길 곳이 없다. `withCredentials`를 켜면 다른 출처에도 자격 증명을 싣는다([WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html), [MDN EventSource()](https://developer.mozilla.org/en-US/docs/Web/API/EventSource/EventSource)) |
| WebSocket | 지원([MDN WebSockets API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)) | 지원([MDN WebSockets API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)) | 조건부: 화면 코드가 직접 만든다. 표준은 닫히면 CLOSED로 두고 close 이벤트를 낸다([WHATWG WebSockets](https://websockets.spec.whatwg.org/)). 다시 붙을 때 첫 시도를 무작위로 늦추고 backoff를 쓰라고 적는다([RFC 6455 7.2.3](https://www.rfc-editor.org/rfc/rfc6455#section-7.2.3)). 이어 받기는 확인하지 않았다 | 해당 없음: 여는 핸드셰이크 뒤로는 TCP 위의 메시지 프레임이다([RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)) | 조건부: 생성자는 URL과 하위 프로토콜만 받는다([WHATWG WebSockets](https://websockets.spec.whatwg.org/), [MDN WebSocket()](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket)). 서버는 쿠키, HTTP 인증, TLS 인증 같은 HTTP 서버의 인증 수단을 쓸 수 있다([RFC 6455 10.5](https://www.rfc-editor.org/rfc/rfc6455#section-10.5)) |

장단점 표는 방식마다 얻는 것, 내주는 것, 브라우저와 서버가 해 주는 것과 코드가 직접 만들어야 하는 것을 견준다. 기능 표에 적은 것은 되풀이하지 않고 "기능 표"로 가리킨다.

| 방식 | 얻는 것 | 내주는 것 | 해 주는 것과 직접 만드는 것 |
|---|---|---|---|
| HTTP + JSON | 자원마다 URL이 있고 그 URL로 캐시를 만든다([GraphQL Caching](https://graphql.org/learn/caching/)의 endpoint 방식 설명). 프록시, 게이트웨이, 터널이 HTTP의 중개자로 정의돼 있다([RFC 9110 3.7](https://www.rfc-editor.org/rfc/rfc9110#section-3.7)). 기능 표의 HTTP 캐시와 인증 헤더 | 서버가 먼저 보내지 못한다(기능 표). 여러 자원을 보이는 화면은 자원마다 왕복한다([Queries](https://graphql.org/learn/queries/)) — 잴 것: 웹 통신 실험의 화면 하나의 왕복 횟수 | 브라우저: 캐시, fetch로 헤더 싣기(기능 표) · 화면 코드: 화면이 보일 자원마다 요청을 보내고 모은다 |
| GraphQL | 응답이 질의와 같은 모양이고, 관련 객체를 한 요청으로 받고, 한 화면의 요약 보기와 자세히 보기를 같은 질의의 필드 차이로 둔다([Queries](https://graphql.org/learn/queries/)) | 기능 표의 HTTP 캐시. URL 같은 전역 식별자가 없어 객체마다 전역 ID를 낸다([Caching](https://graphql.org/learn/caching/)). 파일 올리기를 염두에 두지 않았고 signed URL을 권한다([File Uploads](https://graphql.org/learn/file-uploads/)). subscription은 구독 내내 질의와 변수와 맥락을 들고 있어야 해 query보다 만들기 어렵고, 구독한 클라이언트마다 서버 인스턴스 하나에 고정돼야 해 수평 확장이 어렵고, 아키텍처가 복잡해진다([Subscriptions](https://graphql.org/learn/subscriptions/)) | 서버 코드: N+1을 막는 batching(DataLoader 등)과 무거운 질의를 막는 demand control([Performance](https://graphql.org/learn/performance/)) · 화면 코드: 필요한 필드를 질의로 적는다([Queries](https://graphql.org/learn/queries/)) |
| SSE | 기능 표의 다시 붙기. 보통의 HTTP 응답(`text/event-stream`)이다([MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)). 여러 페이지가 shared worker로 EventSource 하나를 나눠 쓰면 연결 한도를 피할 수 있다고 표준이 적는다([WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)) | 단방향, 인증 헤더(기능 표). 스트림은 UTF-8로 읽힌다. 오래된 프록시는 짧은 시간 뒤 연결을 끊는다([WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)). HTTP/2가 아니면 브라우저와 도메인마다 6개 연결(브라우저의 한도, [MDN Using SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)). nginx는 응답을 모아 보내는 `proxy_buffering`이 기본으로 켜져 있다(제품의 기본값, [nginx proxy](http://nginx.org/en/docs/http/ngx_http_proxy_module.html)) | 브라우저: 다시 붙기, `retry`로 받은 시간만큼 기다리기, `Last-Event-ID` 보내기([MDN Using SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events), [WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)) · 서버 코드: 이벤트에 id를 매기고 그 뒤의 것을 보낸다, 프록시 버퍼링을 끈다(nginx는 응답 헤더 `X-Accel-Buffering`으로도 끈다), 오래된 프록시가 연결을 끊지 않게 주석 줄을 보낸다(간격은 표준의 권고로 15초쯤이다 — WHATWG SSE의 작성자 주의(Authoring notes). 잰 값도 설계 기준도 아니다) · 화면 코드: 다시 붙지 않고 멈춘 경우(200이 아닌 응답)를 알아채고 다시 연다 |
| WebSocket | 한 연결로 양방향, 텍스트와 바이너리([RFC 6455 1.2](https://www.rfc-editor.org/rfc/rfc6455#section-1.2)). 포트 80·443과 HTTP 프록시를 지나도록 설계됐다([RFC 6455 1.1](https://www.rfc-editor.org/rfc/rfc6455#section-1.1)) | 기능 표의 다시 붙기와 인증 헤더. backpressure가 없어 처리보다 빨리 오면 메모리를 채우거나 CPU가 100%가 된다고 MDN이 적고, 그 경우 WebTransport를 쓰라고 적는다([MDN WebSockets API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)). Upgrade는 hop-by-hop 헤더라 리버스 프록시에 따로 설정하고, nginx는 60초 동안 데이터가 없으면 끊는다(제품의 기본값, [nginx WebSocket proxying](http://nginx.org/en/docs/http/websocket.html)) | 브라우저: 연결을 열고 메시지를 주고받고, 닫히면 close 이벤트를 낸다([WHATWG WebSockets](https://websockets.spec.whatwg.org/)) · 서버 코드: 인증(쿠키 등, [RFC 6455 10.5](https://www.rfc-editor.org/rfc/rfc6455#section-10.5)), 프레임과 메시지 크기의 한도([RFC 6455 10.4](https://www.rfc-editor.org/rfc/rfc6455#section-10.4)), 프록시가 끊지 않게 ping을 보낸다([nginx WebSocket proxying](http://nginx.org/en/docs/http/websocket.html)) · 화면 코드: 다시 붙기(backoff)와 이어 받기, 빨리 오는 메시지를 처리하는 속도 맞추기 |
| gRPC-Web (쓰지 않는다 — 1절 gRPC 줄) | 브라우저에서 `.proto`로 만든 클라이언트를 쓴다([grpc-web README](https://github.com/grpc/grpc-web)) | gRPC-Web 요청을 gRPC로 옮기는 프록시가 반드시 있어야 한다(기본은 Envoy). 서버 스트림은 `grpcwebtext` 모드에서만 되고 그 모드는 본문을 base64로 담으며, 클라이언트 스트림과 양방향 스트림은 지원하지 않는다([grpc-web README](https://github.com/grpc/grpc-web)). 브라우저가 HTTP/2 gRPC를 직접 쓰지 못하는 까닭은 요청을 세밀하게 다루는 브라우저 API가 없고 HTTP/2 프레임을 다룰 수 없어서다([The state of gRPC in the browser](https://grpc.io/blog/state-of-grpc-web/), 2019년 글) | 해당 없음(쓰지 않는다) |

## 3. 규모에 따라 달라지는 것

규모의 축마다 방식별로, 규모가 커지면 무엇이 유리해지고 무엇이 문제가 되는지 방향만 적은 표다. 경계값은 적지 않고 "잴 것"으로 둔다. 숫자는 모두 브라우저나 표준이 정한 한도다. 확인한 날: 2026-11-22.

| 축 | HTTP + JSON | GraphQL | SSE | WebSocket |
|---|---|---|---|---|
| 동시 연결 수 | 방향도 잴 것: 웹 통신 실험의 동시 사용자 수별 서버 메모리와 처리량 | query와 mutation은 HTTP 요청이다([Serving over HTTP](https://graphql.org/learn/serving-over-http/)) — 방향도 잴 것: 웹 통신 실험의 동시 사용자 수별 서버 메모리. subscription은 구독한 클라이언트마다 인스턴스 하나에 고정돼야 해 수평 확장이 어렵다고 문서가 적는다([Subscriptions](https://graphql.org/learn/subscriptions/)) — 잴 것: 웹 통신 실험의 구독 수별 서버 메모리 | 브라우저 쪽: HTTP/2가 아니면 브라우저와 도메인마다 6개, HTTP/2면 동시 stream 수를 서버와 브라우저가 정한다(브라우저의 한도, MDN은 기본 100이라 적는다 — [MDN Using SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)). 서버 쪽은 방향도 잴 것: 웹 통신 실험의 연결 수별 서버 메모리 | 클라이언트가 한 호스트에 여는 연결 수에 표준의 한도가 없고, 서버는 연결이 지나치게 많은 곳의 연결을 거절할 수 있다([RFC 6455 4.1](https://www.rfc-editor.org/rfc/rfc6455#section-4.1)). 서버 쪽은 방향도 잴 것: 웹 통신 실험의 연결 수별 서버 메모리 |
| 화면 하나가 보내는 요청 수 | 자원이 늘면 왕복이 는다([Queries](https://graphql.org/learn/queries/)) — 잴 것: 웹 통신 실험의 화면 하나의 왕복 횟수와 다 그려지기까지의 시간 | 관련 객체를 한 요청으로 받는다([Queries](https://graphql.org/learn/queries/)). 서버 안에서는 N+1 조회가 생길 수 있다([Performance](https://graphql.org/learn/performance/)) — 잴 것: 웹 통신 실험의 서버의 조회 횟수(batching 전후) | 연결 하나가 열린 채로 이벤트를 받는다([MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)). 브라우저가 보내는 것은 따로 된 요청이다(기능 표) | 연결 하나로 주고받는다([MDN WebSockets API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)) |
| 응답과 메시지 크기 | 방향도 잴 것: 웹 통신 실험의 응답 크기별 처리량(`service-communication.md`의 크기 실측은 서버 사이에서 잰 것이다) | 응답이 질의와 같은 모양이다([Queries](https://graphql.org/learn/queries/)). 무거운 질의는 데이터 원본에 지나친 부하를 줄 수 있다([Performance](https://graphql.org/learn/performance/)) — 잴 것: 웹 통신 실험의 질의 깊이별 응답 크기와 서버 시간 | 스트림은 UTF-8로 읽힌다([WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)) — 방향도 잴 것: 웹 통신 실험의 바이너리를 텍스트로 담을 때의 크기 | 구현은 메시지 크기에 한도를 둬야 한다([RFC 6455 10.4](https://www.rfc-editor.org/rfc/rfc6455#section-10.4)) — 방향도 잴 것: 웹 통신 실험의 메시지 크기별 처리량 |
| 밀어 주는 빈도 | 해당 없음: 밀어 주지 않는다(기능 표) | subscription은 그 전송 방식의 열 | 방향도 잴 것: 웹 통신 실험의 초당 이벤트 수별 서버 CPU, 프록시 버퍼링이 더하는 지연 | 처리보다 빨리 오면 브라우저의 메모리를 채우거나 CPU가 100%가 된다([MDN WebSockets API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)) — 잴 것: 웹 통신 실험의 초당 메시지 수별 브라우저 메모리 |

## 아직 줄이 없는 것

모바일 앱과 서버의 통신은 따로 된 문서가 정한다(작성 예정). 파일 전송(올리기, 내려받기)과 미디어 스트리밍(영상, 음악)도 따로 된 문서가 정한다(작성 예정). 그때까지 만나면 `ROUTING.md`의 "표에 없는 갈림을 만났을 때" 절차대로 한다. SSE, WebSocket, GraphQL subscription처럼 오래 열린 연결을 여러 인스턴스에 어떻게 나누나는 이 문서가 정하지 않는다 — `load-balancing.md`(작성 예정)가 정한다. 브라우저도 가끔 보내는 화면에서 SSE + HTTP 요청과 WebSocket의 경계는 웹 통신 실험(SSE 줄과 WebSocket 줄 근거의 "잴 것")이 잰 뒤에 정하고, 그때까지는 1절 묻는 경우의 셋째 항목대로 묻는다. HTTP/2 위의 WebSocket과 WebTransport는 확인하지 않아 후보에 넣지 않았다. 함께 편집에서 부딪힌 입력을 어떻게 합치나는 통신 방식의 선택이 아니라 이 문서가 정하지 않는다. 2절 기능 표의 "확인하지 않았다" 칸은 공식 문서에서 확인하면 그 칸을 고친다. 만나면 ROUTING.md의 절차로 정한다.
