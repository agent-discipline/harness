# 웹과 서버의 통신 분기표

우리가 만들어 배포하는 화면(웹 화면, 관리자 화면)이 브라우저에서 우리 서버를 부를 때 어떻게 통신할지 정할 때 읽는다. 우리가 만든 서비스 사이는 [service-communication.md](service-communication.md), 우리가 배포하지 않는 시스템이 우리를 부르는 경우(남이 만든 웹 화면이 브라우저에서 우리 API를 부르는 경우도 든다)는 그 문서 3절, 브라우저와 서버 사이의 암호화(https, wss)는 그 문서 5절이 정한다. 모바일 앱, 파일 전송, 미디어 스트리밍은 이 문서가 정하지 않는다(끝의 "아직 줄이 없는 것"). 줄의 형식과 근거의 종류, 줄이 없거나 부딪힐 때의 절차, 전환 기준은 [ROUTING.md](ROUTING.md)에 있다.

- **근거**: 이 문서의 근거는 모두 사용자 판단과 일반 지식(표준과 공식 문서)이다. 웹 통신을 직접 잰 실측은 없다. 크기가 있는 얻는 것과 내주는 것(연결 수별 메모리, 다시 붙기까지의 시간, 왕복 횟수, 지연, 서버의 조회 횟수, 응답 크기)에는 "잴 것: 웹 통신 실험의 ○○"를 붙였고, 방향조차 문서로 받칠 수 없는 것은 "방향도 잴 것"으로 적었다. 브라우저나 표준, 제품이 정한 고정 한도와 기본값은 "브라우저의 한도", "제품의 기본값"으로 밝히고 출처만 적었다. 웹 통신 실험은 다음 작업이다.
- **낱말**: 호출 — 화면이 서버와 주고받는 것 하나(목록 하나를 받는 것, 저장 하나, 알림의 흐름 하나). 1절은 호출마다 고른다. 운영하는 방식 — 브라우저가 이 호출로 부르는 우리 서버가 이 설계를 시작하기 전에 클라이언트(브라우저, 모바일 앱, 그 밖의 클라이언트)에 이미 열어 운영하던 방식(HTTP + JSON, GraphQL, SSE, WebSocket). 모바일 앱에 연 GraphQL, 다른 화면에서 운영하는 SSE나 WebSocket도 든다. GraphQL subscription이 실려 가는 WebSocket이나 SSE는 운영하는 WebSocket이나 SSE로 세지 않는다 — 그 연결은 subscription의 전송이라, 다른 값을 그 연결로 보내려면 subscription을 새로 만드는 것이고 새 방식을 더하는 일이다. 우리가 운영하는 다른 서버에만 있는 방식은 세지 않는다(새 방식을 더하는 선택지를 보일 때 적는다 — 1절 묻는 경우). SSE는 HTTP 응답이지만 HTTP + JSON의 확장으로 보지 않고 따로 센다(이벤트 id와 그 뒤의 것 보내기, 프록시 버퍼링 끄기 같은 SSE만의 서버 코드가 있다 — 2절 장단점 표). 이번 설계에서 그 서버에 정한 방식(줄을 따라 고른 것, 묻고 승인받은 것)도 같은 설계의 뒤 호출에서는 운영하는 방식으로 센다(1절의 고르는 차례). 센다고 해서 같은 필요를 채운다는 이유로 쓰지는 않는다 — 묻지 않고 쓰는 경우는 1절 머리의 ③이 정하고, 처음 고르는지도 이것으로 바뀌지 않는다. 같은 설계에서 다른 서버에 정한 방식은 세지 않는다(다른 서버에만 있는 방식과 같다). 이 화면이 연 연결 — 이 화면이 이미 열었거나 이번 설계에서 열기로 정한 연결(함께 편집의 WebSocket, 알림의 SSE). 처음 고른다 — 그 서버가 이 설계를 시작하기 전에 어느 클라이언트에도 연 방식이 하나도 없다. 이번 설계에서 방식을 정한 뒤의 호출도 처음 고르는 것이다. 따로 만드는 클라이언트 — 따로 만들고 따로 배포하는 화면의 묶음(웹앱, 모바일 앱, 관리자 화면). 한 웹앱 안의 목록, 상세, 대시보드는 클라이언트 하나다. 다시 붙기 — 끊긴 연결을 다시 여는 것. 이어 받기 — 끊긴 동안 놓친 메시지를 다시 붙은 뒤 받는 것. SSE(server-sent events) — 브라우저가 EventSource로 열고 서버가 이벤트를 이어 보내는 HTTP 응답.

## 1. 어느 방식을 쓰나

호출마다 세 차례로 고른다. ①이 호출의 필요를 아래 세 가지 가운데 하나로 나눈다. ②그 필요에 맞는 줄이 선택을 정한다. ③이 화면이 연 연결이 그 필요를 채우면 그 연결을 쓴다(표의 마지막 줄). 아니면 줄의 선택을 그 서버가 이미 운영할 때 그대로 쓰고, 처음 고를 때 줄의 선택을 따른다. 그 밖에는 묻는다(아래 "줄의 선택을 운영하지 않을 때"와 첫째 항목 — `ROUTING.md` "줄을 따를 때"의 전환 기준). 예외는 HTTP + JSON 줄 하나다(그 문단). 기술을 아는지 묻는 것과 설명 문서, 묻지 않고 지금 것으로 갈 때 더 나은 대안을 적어 두는 것은 `ROUTING.md`의 전환 기준이 정한다. 한 설계에서 고를 호출이 여럿이면 모든 호출의 필요를 먼저 나누고, 두 쪽이 주고받는 호출(WebSocket 줄에 드는 것 먼저), 서버에서 보내는 호출, 묻고 한 번 답하는 호출(GraphQL 줄에 드는 것 먼저)의 차례로 고른다. 여러 필요를 채우는 방식을 먼저 골라야 뒤의 호출이 그것을 다시 쓰고(같은 화면이 연 연결, 예외의 GraphQL), 설계하는 사람이 어느 호출부터 보든 결과가 같다. 앞의 호출에서 정한 방식은 뒤 호출에서 운영하는 방식으로 세지만, 묻지 않고 그것을 쓰는 것은 그것이 이 화면이 연 연결이거나 뒤 호출의 줄이 가리키는 방식 그 자체일 때(그리고 예외에 들 때)뿐이다. 그 밖에는 처음 고르는 설계면 줄을 따르고 처음 고르는 것이 아니면 묻는다. 앞의 호출에서 묻고 승인받은 것은 같은 설계에서 다시 묻지 않는다. 어느 줄을 고르든 고른 방식이 필요한 기능을 모두 채우는지 2절 기능 표에서 본다. 파일 전송과 미디어 스트리밍은 운영하는 방식으로 보낼 수 있더라도 어느 줄에도 들지 않는다(끝의 "아직 줄이 없는 것").

필요는 셋이다. 호출 하나는 이 가운데 하나에만 든다.

- **묻고 한 번 답한다**: 브라우저가 요청 하나를 보내고 서버가 그 요청에 응답 하나를 보내면 호출이 끝난다. 읽는 것(목록, 상세, 이력)과 바꾸는 것(저장, 삭제)이 모두 여기다.
- **서버에서 보낸다**: 브라우저가 한 번 열면 서버가 값이 생길 때마다 보낸다(알림, 진행률, 상태 변화, 접속자 표시). 화면이 무언가 보내더라도 그것이 다른 사람의 화면에 닿지 않으면 여기이고, 보내는 것은 따로 된 묻고 한 번 답하는 호출이다(진행률 화면의 취소, 알림의 읽음 표시). 다른 화면에서 쓴 것을 받기만 하는 화면도 여기다(관리자 화면에서 쓴 공지를 사용자 화면들이 받는다 — 공지 쓰기는 묻고 한 번 답하는 호출인 저장이다).
- **두 쪽이 주고받는다**: 같은 화면이 보내기도 하고, 다른 사람이 보낸 것을 받기도 한다 — 이 화면에서 보낸 것이 다른 사람의 화면에 닿는다(함께 편집의 입력, 채팅, 좋아요). 이 가운데 한 연결로 주고받아야 하는 것과 서버에서 보내는 흐름에 따로 된 요청을 더하면 되는 것은 경계값 없이 구분하지 못한다. 그래서 WebSocket 줄은 함께 편집의 입력만 정하고, 나머지는 아래 셋째 항목대로 묻는다.

같은 필요를 채운다고 보는 것은 이렇다. 묻고 한 번 답하는 필요는 HTTP + JSON과 GraphQL의 query·mutation이 채운다. WebSocket과 SSE는 채운다고 보지 않는다. 이 필요의 줄이 얻는 것은 GET 응답의 HTTP 캐시인데 두 방식에는 그것이 없기 때문이다(2절 기능 표). 서버에서 보내는 필요는 SSE, WebSocket, 그 값을 보내는 GraphQL subscription이 채운다. 두 쪽이 주고받는 필요는 WebSocket이 채우고, 함께 편집의 입력이 아닌 것(셋째 항목)은 SSE와 HTTP + JSON을 함께 운영하는 것도 채운다. HTTP + JSON으로 일정 간격마다 다시 묻는 것은 서버에서 보내는 필요를 채우는 것이 아니라, 묻는 경우의 선택지 가운데 지금 것으로 채우는 안이다.

**줄의 선택을 운영하지 않을 때.** 처음 고르는 것이 아니고 이 화면이 연 연결도 이 호출의 필요를 채우지 못하는데 줄이 가리키는 방식을 그 서버가 운영하지 않으면, 운영하는 다른 방식(다른 화면이나 모바일 앱에 연 것)이 같은 필요를 채우더라도 조용히 그것으로 가지 않고 묻는다(아래 첫째 항목). 같은 필요를 채우는 방식은 선택지에 들 뿐, 고를 근거가 되지 않는다. 예: 채팅용 WebSocket을 운영하는 서버에 새 "배포 진행률" 화면(SSE 줄)이 생기면 묻는다 — SSE를 들이면 브라우저가 스스로 다시 붙고 서버가 이벤트 id 뒤의 것을 보내면 이어 받는다, WebSocket으로 채우면 방식이 늘지 않지만 다시 붙기와 이어 받기를 직접 만든다. 예외는 하나다. 줄이 HTTP + JSON 줄이고(다른 줄에 들지 않아 기본으로 왔다) 그 서버가 HTTP + JSON은 운영하지 않고 GraphQL을 운영하면, 묻지 않고 GraphQL을 쓴다(표의 마지막 줄). 더하는 기술이 없고, HTTP + JSON 줄의 조건은 GraphQL 줄에 들지 않는다는 것뿐이기 때문이다.

- 헤더로 인증을 실어야 하는데 고른 줄이나 쓰려는 연결이 SSE나 WebSocket이다(2절 기능 표의 인증 헤더 칸이 "안 된다"). 선택지는 같은 출처에 두고 쿠키로 인증한다(EventSource는 `withCredentials`를 켜면 다른 출처의 요청에도 자격 증명을 싣고, WebSocket 서버는 쿠키 같은 HTTP 서버의 인증 수단을 쓸 수 있다) / EventSource 대신 fetch로 SSE 응답을 스트림으로 읽는다(헤더를 싣는 대신, EventSource가 해 주던 다시 붙기와 `Last-Event-ID`를 화면 코드가 직접 만든다) / 토큰을 URL에 싣는다(URL에 실은 토큰은 로그에 남을 가능성이 커서, RFC 6750은 `Authorization` 헤더나 본문으로 보낼 수 없을 때만 쓰라고 적고, 브라우저 기록과 웹 서버 로그에서 토큰을 훔칠 수 있다고 적는다 — [RFC 6750 2.3](https://www.rfc-editor.org/rfc/rfc6750#section-2.3), [5.3](https://www.rfc-editor.org/rfc/rfc6750#section-5.3))이다. 로그인이 만료되어 다시 붙을 때 401이 오면 EventSource가 멈추므로, 화면이 이것을 알아채고 다시 여는 방법도 함께 정한다.
- 고른 방식이 2절 기능 표에서 조건부의 조건을 채우지 못하거나, 조건끼리 부딪히거나, "확인하지 않았다"에 걸린다.
- 브라우저가 쓸 기능이 gRPC 서비스에만 있는데, 브라우저가 부를 서버를 새로 둬야 하거나 그 gRPC 서비스가 HTTP + JSON도 함께 열어야 할 것 같다(gRPC 줄). 구성 요소를 더하는 것이라 메인이 고르지 않는다. 전환 기준대로 선택지는 브라우저가 이미 부르는 서버가 있으면 그 서버가 안에서 gRPC를 부른다(지금 가진 것으로 채우는 안 — 얻는 것과 내주는 것은 gRPC 줄), 그런 서버가 없으면 브라우저가 부를 서버를 새로 둔다(운영할 서버가 하나 늘고, 그 서버를 거치는 만큼 지연이 는다 — 크기는 잴 것) / 그 gRPC 서비스가 HTTP + JSON도 함께 연다(한 서비스가 HTTP와 gRPC 두 가지를 함께 연다) / 작은 실험으로 견준 뒤 정한다(두 안에서 브라우저가 응답을 받기까지의 지연을 잰다. 드는 시간은 물을 때 적는다)이고, 메인이 권하는 안과 근거를 밝혀 승인받는다.

## 2. 방식별 기능과 장단점

선택이 없는 사실만 모은 두 표다. 확인한 날: 2026-11-22(두 표 모두. 기능 표의 WebSocket 다시 붙기 칸과 장단점 표의 SSE 주석 줄 링크는 2026-11-23).

기능 표는 고른 방식이나 운영하는 방식이 필요한 기능을 채우는지 볼 때 쓴다. 칸의 값은 지원, 조건부(조건을 적었다), 확인하지 않았다(지원하지 않는다는 뜻이 아니다), 안 된다(출처가 그렇게 적었다), 해당 없음(그 방식에서는 물음이 성립하지 않는다) 다섯이다.

| 방식 | 서버가 먼저 보내기 | 브라우저가 그 연결로 계속 보내기 | 다시 붙기와 이어 받기 | HTTP 캐시 | 인증 헤더 |
|---|---|---|---|---|---|
| HTTP + JSON | 해당 없음: 서버는 요청에 응답을 보낸다([RFC 9110 3.3](https://www.rfc-editor.org/rfc/rfc9110#section-3.3)) | 해당 없음: 요청마다 따로 보낸다([RFC 9110 3.3](https://www.rfc-editor.org/rfc/rfc9110#section-3.3)) | 해당 없음: 요청마다 새로 보낸다([RFC 9110 3.3](https://www.rfc-editor.org/rfc/rfc9110#section-3.3)) | 지원: 흔히 쓰는 HTTP 캐시는 GET 응답을 URI를 키로 둔다([RFC 9111](https://www.rfc-editor.org/rfc/rfc9111)). 공유 캐시는 `Authorization`이 실린 요청의 응답을 허락하는 지시가 있을 때만 다시 쓴다([RFC 9111 3.5](https://www.rfc-editor.org/rfc/rfc9111#section-3.5), [MDN HTTP caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)) | 지원: fetch의 `headers`([MDN Using Fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)). 다른 출처면 preflight가 먼저 간다([MDN CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)) |
| GraphQL | 조건부: subscription. 전송은 GraphQL이 정하지 않고 보통 WebSocket이나 SSE를 쓴다([Subscriptions](https://graphql.org/learn/subscriptions/)) — 그 방식의 행 | 확인하지 않았다 | 조건부: subscription은 끊기면 클라이언트 라이브러리가 다시 구독하는 로직이 필요하다([Subscriptions](https://graphql.org/learn/subscriptions/)). 이어 받기는 확인하지 않았다 | 조건부: 기본은 한 엔드포인트의 POST다([Serving over HTTP](https://graphql.org/learn/serving-over-http/), POST 응답의 캐시 조건은 [RFC 9110 9.3.3](https://www.rfc-editor.org/rfc/rfc9110#section-9.3.3)). query를 GET으로 받고 캐시 헤더를 주면 HTTP 캐시와 CDN을 쓰지만, URL 길이 한도 때문에 persisted query가 필요할 수 있다([Performance](https://graphql.org/learn/performance/)) | 지원: query와 mutation은 HTTP POST라([Serving over HTTP](https://graphql.org/learn/serving-over-http/)) fetch의 `headers`로 싣는다([MDN Using Fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)). subscription은 그 전송 방식의 행 |
| SSE | 지원([MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)) | 안 된다: 서버에서 브라우저로만 가는 단방향이다([MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)) | 조건부: 브라우저 — 다시 붙고 `Last-Event-ID`를 보낸다. 서버 — 그 id 뒤의 것을 보내는 것은 서버 코드가 만든다. 응답이 200이 아니거나 `Content-Type`이 `text/event-stream`이 아니면 다시 붙지 않는다([WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)) | 안 된다: EventSource의 요청은 cache mode가 `no-store`다([WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)) | 안 된다: 생성자가 받는 것은 URL과 `withCredentials`뿐이라 헤더를 넘길 곳이 없다. 헤더가 아닌 자격 증명(쿠키)은 `withCredentials`를 켜면 다른 출처에도 싣는다([WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html), [MDN EventSource()](https://developer.mozilla.org/en-US/docs/Web/API/EventSource/EventSource)) |
| WebSocket | 지원([MDN WebSockets API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)) | 지원([MDN WebSockets API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)) | 조건부: 화면 코드가 직접 만든다. 표준은 닫히면 CLOSED로 두고 close 이벤트를 낸다([WHATWG WebSockets](https://websockets.spec.whatwg.org/)). 다시 붙을 때 첫 시도를 무작위로 늦추고 backoff를 쓰라고 적는다([RFC 6455 7.2.3](https://www.rfc-editor.org/rfc/rfc6455#section-7.2.3)). 다시 붙는 동작과 이어 받기(놓친 메시지를 다시 보내기, 마지막으로 받은 위치)는 두 표준에 적혀 있지 않다(화면 코드와 서버 코드가 직접 만든다) | 해당 없음: 여는 핸드셰이크 뒤로는 TCP 위의 메시지 프레임이다([RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)) | 안 된다: 생성자는 URL과 하위 프로토콜만 받아 헤더를 넘길 곳이 없다([WHATWG WebSockets](https://websockets.spec.whatwg.org/), [MDN WebSocket()](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket)). 서버는 쿠키, HTTP 인증, TLS 인증 같은 HTTP 서버의 인증 수단을 쓸 수 있다([RFC 6455 10.5](https://www.rfc-editor.org/rfc/rfc6455#section-10.5)) |

장단점 표는 방식마다 얻는 것, 내주는 것, 브라우저와 서버가 해 주는 것과 코드가 직접 만들어야 하는 것을 견준다. 기능 표에 적은 것은 되풀이하지 않고 "기능 표"로 가리킨다.

| 방식 | 얻는 것 | 내주는 것 | 해 주는 것과 직접 만드는 것 |
|---|---|---|---|
| HTTP + JSON | 자원마다 URL이 있고 그 URL로 캐시를 만든다([GraphQL Caching](https://graphql.org/learn/caching/)의 endpoint 방식 설명). 프록시, 게이트웨이, 터널이 HTTP의 중개자로 정의돼 있다([RFC 9110 3.7](https://www.rfc-editor.org/rfc/rfc9110#section-3.7)). 기능 표의 HTTP 캐시와 인증 헤더 | 서버가 먼저 보내지 못한다(기능 표). 여러 자원을 보이는 화면은 자원마다 왕복한다([Queries](https://graphql.org/learn/queries/)) — 잴 것: 웹 통신 실험의 화면 하나의 왕복 횟수 | 브라우저: 캐시, fetch로 헤더 싣기(기능 표) · 화면 코드: 화면이 보일 자원마다 요청을 보내고 모은다 |
| GraphQL | 응답이 질의와 같은 모양이고, 관련 객체를 한 요청으로 받고, 한 화면의 요약 보기와 자세히 보기를 같은 질의의 필드 차이로 둔다([Queries](https://graphql.org/learn/queries/)) | 기능 표의 HTTP 캐시. URL 같은 전역 식별자가 없어 객체마다 전역 ID를 낸다([Caching](https://graphql.org/learn/caching/)). 파일 올리기를 염두에 두지 않았고 signed URL을 권한다([File Uploads](https://graphql.org/learn/file-uploads/)). subscription은 구독 내내 질의와 변수와 맥락을 들고 있어야 해 query보다 만들기 어렵고, 구독한 클라이언트마다 서버 인스턴스 하나에 고정돼야 해 수평 확장이 어렵고, 아키텍처가 복잡해진다([Subscriptions](https://graphql.org/learn/subscriptions/)) | 서버 코드: N+1을 막는 batching(DataLoader 등)과 무거운 질의를 막는 demand control([Performance](https://graphql.org/learn/performance/)) · 화면 코드: 필요한 필드를 질의로 적는다([Queries](https://graphql.org/learn/queries/)) |
| SSE | 기능 표의 다시 붙기. 보통의 HTTP 응답(`text/event-stream`)이다([MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)). 여러 페이지가 shared worker로 EventSource 하나를 나눠 쓰면 연결 한도를 피할 수 있다고 표준이 적는다([WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)) | 단방향, 인증 헤더(기능 표). 스트림은 UTF-8로 읽힌다. 오래된 프록시는 짧은 시간 뒤 연결을 끊는다([WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)). HTTP/2가 아니면 브라우저와 도메인마다 6개 연결(브라우저의 한도, [MDN Using SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)). nginx는 응답을 모아 보내는 `proxy_buffering`이 기본으로 켜져 있다(제품의 기본값, [nginx proxy](http://nginx.org/en/docs/http/ngx_http_proxy_module.html)) | 브라우저: 다시 붙기, `retry`로 받은 시간만큼 기다리기, `Last-Event-ID` 보내기([MDN Using SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events), [WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)) · 서버 코드: 이벤트에 id를 매기고 그 뒤의 것을 보낸다, 프록시 버퍼링을 끈다(nginx는 응답 헤더 `X-Accel-Buffering`으로도 끈다), 오래된 프록시가 연결을 끊지 않게 주석 줄을 보낸다(간격은 표준의 권고로 15초쯤이다 — [WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)의 작성자 주의(Authoring notes). 잰 값도 설계 기준도 아니다) · 화면 코드: 다시 붙지 않고 멈춘 경우(200이 아닌 응답)를 알아채고 다시 연다 |
| WebSocket | 한 연결로 양방향, 텍스트와 바이너리([RFC 6455 1.2](https://www.rfc-editor.org/rfc/rfc6455#section-1.2)). 포트 80·443과 HTTP 프록시를 지나도록 설계됐다([RFC 6455 1.1](https://www.rfc-editor.org/rfc/rfc6455#section-1.1)) | 기능 표의 다시 붙기와 인증 헤더. backpressure가 없어 처리보다 빨리 오면 메모리를 채우거나 CPU가 100%가 된다고 MDN이 적고, 그 경우 WebTransport를 쓰라고 적는다([MDN WebSockets API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)). Upgrade는 hop-by-hop 헤더라 리버스 프록시에 따로 설정하고, nginx는 60초 동안 데이터가 없으면 끊는다(제품의 기본값, [nginx WebSocket proxying](http://nginx.org/en/docs/http/websocket.html)) | 브라우저: 연결을 열고 메시지를 주고받고, 닫히면 close 이벤트를 낸다([WHATWG WebSockets](https://websockets.spec.whatwg.org/)) · 서버 코드: 인증(쿠키 등, [RFC 6455 10.5](https://www.rfc-editor.org/rfc/rfc6455#section-10.5)), 프레임과 메시지 크기의 한도([RFC 6455 10.4](https://www.rfc-editor.org/rfc/rfc6455#section-10.4)), 프록시가 끊지 않게 ping을 보낸다([nginx WebSocket proxying](http://nginx.org/en/docs/http/websocket.html)) · 화면 코드: 다시 붙기(backoff)와 이어 받기, 빨리 오는 메시지를 처리하는 속도 맞추기 |
| gRPC-Web (쓰지 않는다 — 1절 gRPC 줄) | 브라우저에서 `.proto`로 만든 클라이언트를 쓴다([grpc-web README](https://github.com/grpc/grpc-web)) | gRPC-Web 요청을 gRPC로 옮기는 프록시가 반드시 있어야 한다(기본은 Envoy). 서버 스트림은 `grpcwebtext` 모드에서만 되고 그 모드는 본문을 base64로 담으며, 클라이언트 스트림과 양방향 스트림은 지원하지 않는다([grpc-web README](https://github.com/grpc/grpc-web)). 브라우저가 HTTP/2 gRPC를 직접 쓰지 못하는 까닭은 요청을 세밀하게 다루는 브라우저 API가 없고 HTTP/2 프레임을 다룰 수 없어서다([The state of gRPC in the browser](https://grpc.io/blog/state-of-grpc-web/), 2019년 글) | 해당 없음(쓰지 않는다) |

## 3. 규모에 따라 달라지는 것

규모의 축마다 방식별로, 규모가 커지면 무엇이 유리해지고 무엇이 문제가 되는지 방향만 적은 표다. 경계값은 적지 않고 "잴 것"으로 둔다. 연결 수의 숫자 가운데 6개는 브라우저의 한도이고, 기본 100은 HTTP/2에서 서버와 클라이언트가 협상하는 동시 stream 수의 기본값이라고 MDN이 적은 것이며, "CPU가 100%"는 MDN이 적은 증상이다. 확인한 날: 2026-11-22.

| 축 | HTTP + JSON | GraphQL | SSE | WebSocket |
|---|---|---|---|---|

## 아직 줄이 없는 것

모바일 앱과 서버의 통신은 따로 된 문서가 정한다(작성 예정). 파일 전송(올리기, 내려받기)과 미디어 스트리밍(영상, 음악)도 따로 된 문서가 정한다(작성 예정). 그때까지 만나면 `ROUTING.md`의 "표에 없는 갈림을 만났을 때" 절차대로 한다. SSE, WebSocket, GraphQL subscription처럼 오래 열린 연결을 여러 인스턴스에 어떻게 나누나는 이 문서가 정하지 않는다 — `load-balancing.md`(작성 예정)가 정한다. 두 쪽이 주고받는 것 가운데 함께 편집의 입력이 아닌 것(채팅, 좋아요)에서 SSE + HTTP 요청과 WebSocket의 경계는 웹 통신 실험(SSE 줄과 WebSocket 줄 근거의 "잴 것")이 잰 뒤에 정하고, 그때까지는 1절 묻는 경우의 셋째 항목대로 묻는다. HTTP/2 위의 WebSocket과 WebTransport는 확인하지 않아 후보에 넣지 않았다. 함께 편집에서 부딪힌 입력을 어떻게 합치나는 통신 방식의 선택이 아니라 이 문서가 정하지 않는다. 2절 기능 표의 "확인하지 않았다" 칸은 공식 문서에서 확인하면 그 칸을 고친다. 만나면 ROUTING.md의 절차로 정한다.
