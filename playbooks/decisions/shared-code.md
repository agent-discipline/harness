# 같은 코드가 여러 곳에 생겼을 때 어디로 빼나

같은 코드가 여러 곳에 생겨 한곳으로 뺄지, 뺀다면 어디로 뺄지 정할 때 읽는다. `ROUTING.md`의 "백엔드의 구조를 어떻게 짜나" 가운데 공유로 빼는 것만 먼저 떼어 적은 문서다. 줄의 형식과 근거의 종류, 줄이 없거나 부딪힐 때의 절차는 [ROUTING.md](ROUTING.md)에 있다. 옮기거나 합칠 때의 절차(하던 입력 검증과 에러 처리를 그대로 하고, 원본마다 대조표를 남긴다)는 [`../build-less.md`](../build-less.md) §3이고, 리팩토링으로 연 작업이면 `../refactoring.md`의 고정 순서가 앞선다.

- **근거**: 이 문서의 근거는 사용자 판단(2026-11-22)과 일반 지식이다. 직접 잰 실측은 없다. 두 줄의 얻는 것과 내주는 것은 크기가 없는 사실(고칠 곳이 몇 군데인가, 버전과 올리기가 생기는가)이라 "잴 것"을 붙이지 않았다.
- **낱말**: 같은 규칙 — 같은 입력에 같은 결과를 내야 하는 업무 규칙이나 계산이라서, 한쪽만 바뀌면 둘 가운데 하나가 틀린 상태가 되는 것. 생긴 모양만 같은 것은 같은 규칙이 아니다(2절).

## 1. 어디로 빼나

| 상황 | 선택 | 얻는 것 | 내주는 것 | 근거 | 확인한 날 |
|---|---|---|---|---|---|
| 한 저장소의 두 곳 이상에 같은 규칙이 있고, 한쪽만 바뀌면 틀린 상태가 된다 | 같은 저장소의 공유 폴더(또는 공유 파일)로 옮기고, 원래 있던 곳들이 그것을 부른다. 폴더와 파일 이름은 담긴 도메인 개념으로 짓는다(`common`·`util`을 피한다 — `../design-taste.md` §6) | 그 규칙을 고칠 곳이 한 곳이 되어, 한 번 고치면 부르는 곳 모두에 닿는다 | 부르는 곳이 모두 공유 코드에 기댄다. 한 곳만 다르게 바뀌어야 하는 때가 오면 공유 코드를 다시 갈라내야 한다 | 사용자 판단 2026-11-22(선택 — 중복은 공유 폴더로, 여러 저장소면 라이브러리로) · 일반 지식: Fowler, *Refactoring* 2판 3장의 Duplicated Code와 Shotgun Surgery(한 변경에 여러 곳을 고쳐야 하는 냄새 — `../design-taste.md` §3이 든 출처), 같은 장의 Divergent Change(한 모듈이 서로 다른 이유로 바뀌는 냄새 — 내주는 것) | 2026-11-23 |
| 같은 코드를 여러 저장소(따로 배포하는 단위)가 쓴다 | 라이브러리(패키지)로 만들어 각 저장소가 의존한다. 새 저장소나 새 배포물을 더하는 것이면 고르지 않고 `ROUTING.md` 전환 기준대로 선택지(복사본을 그대로 둔다 / 라이브러리로 만든다 / 작은 실험으로 견준 뒤 정한다)를 보이고 승인받는다. 명세 7절의 답은 여기에 앞서지 않는다 — 7절은 남이 만든 의존성과 기술을 더하는 것을 정하고, 저장소와 배포물을 새로 만드는 것은 정하지 않는다 | 저장소 사이에서도 고칠 곳이 한 곳이 된다 | 라이브러리에 버전이 생긴다. 고친 것은 새 버전으로 내야 하고, 쓰는 저장소마다 그 버전으로 올려야 바뀐 것이 닿는다. 의존 버전을 좁게 묶으면 올리기 어려워지고(version lock), 느슨하게 묶으면 원치 않은 버전이 들어온다(version promiscuity) | 사용자 판단 2026-11-22(선택) · 일반 지식: [Semantic Versioning 2.0.0](https://semver.org/) 머리말(dependency hell, version lock, version promiscuity)과 규칙 3(낸 버전의 내용은 바꾸지 않고, 고친 것은 새 버전으로 낸다) | 2026-11-23 |

어느 줄에 드는지 가를 수 없으면(같은 규칙인지, 바뀌는 이유가 다른지 가를 수 없으면) 고르지 않고 `ROUTING.md`의 "줄을 따를 때"대로 사용자에게 묻는다.

## 2. 아직 줄이 없는 것

- 생긴 모양은 같지만 바뀌는 이유가 다른 코드를 묶을지는 정하지 않았다 — 만나면 `ROUTING.md`의 "표에 없는 갈림을 만났을 때" 절차대로 묻는다.
