# 서비스 간 통신 분기표

우리가 만든 서비스들이 서로 어떻게 통신할지 정할 때 읽는다. 위에서부터 차례로 묻고, 해당하는 줄의 선택을 따른다. 줄의 형식과 근거의 종류, 줄이 없거나 부딪힐 때의 절차는 [ROUTING.md](ROUTING.md)에 있다. 우리가 외부 시스템을 부르는 경우는 이 문서가 아니라 외부 연계 문서(작성 예정)의 일이다.

- **내부 서비스**: 우리가 배포하고 같은 사설망에 둔 서비스. **밖에서 부르는 쪽**: 브라우저, 관리자 화면, 우리가 배포하지 않는 시스템.
- **실측의 조건**: 실측은 모두 `http-grpc-lab`(`main` `3f7c856`)의 `docs/remeasure/RESULT.md`와 `docs/remeasure/tables/`의 값이다. k6와 두 서버(apiServer가 dataServer를 부른다)가 한 머신(24코어)에서 돌고, 두 서버 사이는 호스트 실행이면 localhost, 지연 조건이면 컨테이너 사이에 `tc netem`으로 0·1·10ms(왕복 하나에 그만큼 더해진다)를 건다. TLS 없음, 서버당 인스턴스 하나, 조건마다 5회 × 30초. 값은 처리량(req/s) 또는 p95(ms)의 5회 중앙값이고 대괄호는 5회의 최소\~최대다. "5/5"는 다섯 회차 모두 그 경로가 1위라는 뜻이고, 1위가 회차마다 바뀌면 "차이 없음"이다. 절대값은 이 머신의 것이므로 방식 사이의 상대 차이만 본다. 서로 다른 축의 표끼리는 견주지 않는다.
- **축과 경로**: 크기 축(`size-nodelay.md`, 동시 10, 1KB\~1MB) · 동시 사용자 축(`concurrency-default-nodelay.md`, `concurrency-matched-nodelay.md`, 10KB, 동시 10\~500. default는 기본 스레드 상한, matched는 연결과 스레드의 상한을 512로 맞춘 설정) · 복잡도 축(`complexity-nodelay.md`, 동시 10, 구조가 있는 데이터 simple\~extreme) · 지연 조건(`size-delay0ms.md`, `size-delay1ms.md`, `size-delay10ms.md`, 크기 축). 경로: `http-json`(HTTP/1.1 + JSON. 크기 축과 동시 사용자 축에서는 바이트를 Base64로 담는다) · `http-bytes`(HTTP/1.1 + 원시 바이트) · `http-proto`(HTTP/1.1 + Protobuf) · `grpc-unary`(같은 Protobuf 메시지를 gRPC로). 스트림과 TLS는 재지 않았다.

## 3. 누가 부르는가 (동기 호출)

4절에 해당하는 줄이 있으면 4절이 이 절보다 앞선다. gRPC를 고르는 경우는 넷이다: 스트림이 필요하다(4절의 "계속 밀어 준다" 줄), 그리고 아래 표의 셋.

| 상황 | 선택 | 얻는 것 | 내주는 것 | 근거 | 확인한 날 |
|---|---|---|---|---|---|
| 내부 서비스가 내부 서비스를 부른다 (아래 gRPC 줄과 4절에 들지 않는다) | HTTP + JSON (기본). 본문 형식은 아래 본문 형식 줄 | 전송만 견주면(같은 Protobuf 메시지를 `http-proto`와 `grpc-unary`로) 처리량은 10KB 동시 10\~500에서 두 설정 모두 차이 없음, 100KB\~1MB에서는 HTTP가 5/5로 높다(`grpc-unary` ÷ `http-proto` − 1 = −7.2%\~−45.0%). 분산 장치를 따로 정하지 않아도 된다(아래 조건 줄) | 아래 gRPC 줄의 얻는 것(기한·취소의 전파, 언어 사이의 계약 생성, p95). 전송만 견주어 gRPC가 5/5로 높은 조건도 있다: 크기 축 10KB +7.8%, 복잡도 축 medium +10.8% | 사용자 판단 2026-11-22 · 실측(`concurrency-default-nodelay.md:42-46`, `concurrency-matched-nodelay.md:42-46`, `size-nodelay.md:44-50`, `complexity-nodelay.md:42-46`) | 2026-11-22 |
| 여러 팀과 여러 언어가 계약을 공유한다 | gRPC 단건 호출 | `.proto` 스키마가 계약이 되고, 언어마다 클라이언트와 서버 코드를 생성한다 | 아래 조건 줄의 분산 장치. 응답이 100KB 이상이면 처리량이 `http-proto`보다 7.2%\~45.0% 낮다(크기 축, 5/5) | 사용자 판단 2026-11-22 · 일반 지식([gRPC 소개](https://grpc.io/docs/what-is-grpc/introduction/), [핵심 개념](https://grpc.io/docs/what-is-grpc/core-concepts/)) · 실측(`size-nodelay.md:47-50`) | 2026-11-22 |
| 기한과 취소를 호출 사슬로 전파해야 한다 | gRPC 단건 호출 | 들어온 호출의 기한이 나가는 호출로 넘어가고(Java, Go는 기본), 취소도 나가는 호출로 넘어간다 | 위 줄과 같다(분산 장치, 100KB 이상의 처리량) | 사용자 판단 2026-11-22 · 일반 지식([Deadlines](https://grpc.io/docs/guides/deadlines/), [Cancellation](https://grpc.io/docs/guides/cancellation/)) · 실측(위 줄) | 2026-11-22 |
| p95 지연이 중요하다 (동시 100\~200명) | gRPC 단건 호출 | matched에서 p95가 가장 낮은 회차가 5/5: 동시 100 15.818 대 `http-proto` 18.452ms, 동시 200 31.093 대 36.347ms. default는 4/5(차이 없음 — 15.350 대 17.075, 27.403 대 34.199ms) | 처리량은 같음(동시 100·200 두 설정 모두 차이 없음). 동시 500에서는 p95도 차이 없음(default 4/5, matched는 회차마다 달라짐). 분산 장치와 100KB 이상의 처리량은 위 줄과 같다 | 사용자 판단 2026-11-22 · 실측(10KB, `concurrency-matched-nodelay.md:78-84,90-96,102-108`, `concurrency-default-nodelay.md:78-84,90-96,102-108`) | 2026-11-22 |
| gRPC를 골랐고, 불리는 쪽 인스턴스가 둘 이상이다 | 요청 단위 분산 장치(L7 프록시, 클라이언트 쪽 분산, 연결 수명 제한 가운데 하나)를 함께 정한다. 정하지 못하면 HTTP로 둔다 | 한 HTTP/2 연결의 요청이 여러 인스턴스로 나뉜다 | 분산 장치 하나를 더 정하고 운영한다(L7 프록시면 거치는 곳이 하나 는다) | 사용자 판단 2026-11-22 · 일반 지식([gRPC Load Balancing](https://grpc.io/blog/grpc-load-balancing/), [A9 MAX_CONNECTION_AGE](https://github.com/grpc/proposal/blob/master/A9-server-side-conn-mgt.md)) · 잴 것: http-grpc-lab의 인스턴스 여러 개 실험에서 요청이 한 인스턴스에 몰리는 정도, 분산 장치가 더하는 지연 | 2026-11-22 |

## 규칙으로 쓰지 않는 것

예전 실험 README의 가이드에 있던 문장이다. 다시 쟀더니 재현되지 않아 줄로 넣지 않는다(RESULT.md "예전 결론 가운데 재현되지 않은 것").

- "필드가 150개 이상이면 HTTP가 낫다": ultra와 extreme에서도 Protobuf 두 경로는 차이 없음(`grpc-unary` 4/5)이고, `http-json`이 가장 낮다(ultra 2,192 대 `http-proto` 3,100, extreme 361 대 861 — `complexity-nodelay.md:35-36`).
- "동시 사용자가 200명 이상이면 gRPC가 낫다": 동시 200과 500에서 두 설정 모두 처리량의 1위가 회차마다 바뀌었고, `grpc-unary`가 `http-proto`를 5/5로 앞선 조건은 이 축에 없다(`concurrency-*-nodelay.md:35-36,45-46`).
- "100KB 이하에서 gRPC가 30\~67% 빠르다": `grpc-unary`가 5/5로 앞선 것은 10KB 하나이고 폭은 `http-proto`보다 7.8%다. 1KB와 50KB는 차이 없음, 100KB는 `http-bytes`가 5/5 1위다(`size-nodelay.md:32-35,45`).
- 복잡한 데이터에서의 gRPC 스트림 수치: 단건과 같은 코드를 잰 값이라 쓰지 않는다.
