# 서비스 간 통신 분기표

서비스와 서비스가 어떻게 통신할지 정할 때 읽는다. 위에서부터 차례로 묻고, 해당하는 줄의 선택을 따른다. 줄의 형식과 근거의 종류, 줄이 없을 때의 절차는 [ROUTING.md](ROUTING.md)에 있다.

실측의 출처는 `lab/network-labs/http-grpc-lab`이다. **이 실험은 한 머신의 localhost에서 TLS 없이, 서버당 인스턴스 하나로, 조건당 1~3회 쟀고, 같은 조건에서도 값이 위아래로 20%쯤 흔들렸다.** 서비스 사이에 네트워크 지연이 있는 조건은 재지 않았다. 아래에서 "실측(다시 재는 중)"이라고 적은 줄은 모두 이 조건의 값이다.

## 1. 함께 성공하거나 함께 실패해야 하는가

여러 서비스에 걸친 작업이면 통신 방식보다 이것을 먼저 정한다.

| 상황 | 선택 | 이유 | 근거 | 확인한 날 |
|---|---|---|---|---|
| 나중에 맞춰지면 된다 (한쪽이 먼저 끝나도 된다) | 2절로 간다 | 일관성을 지키는 장치가 필요 없다 | 사용자 판단 2026-11-20 | 2026-11-20 |
| 함께 성공하거나 실패해야 하고, 한 서비스의 한 트랜잭션에 둘 수 있다 | 한 트랜잭션에서 처리한다. 서비스 사이의 호출을 없앤다 | 가장 싸게 일관성을 얻는다. 서비스의 경계를 먼저 다시 본다 | 사용자 판단 2026-11-20 | 2026-11-20 |
| 함께 성공하거나 실패해야 하는데, 한 트랜잭션에 둘 수 없거나 작업이 너무 길어진다 | 사가: 단계마다 확정하고, 실패하면 앞 단계를 보상한다. 단계 사이의 전달은 Outbox와 Inbox | 긴 트랜잭션으로 묶지 않고 일관성을 맞춘다. 치르는 비용은 보상 동작의 설계, 중간 상태가 밖에 보이는 것, 중복 수신의 멱등 처리 | 사용자 판단 2026-11-20 · 재 본 적 없음 | 2026-11-20 |

사가의 세부(어디까지 보상하나, 중간 상태를 어떻게 보이나, 단계를 누가 조율하나)는 아직 줄이 없다. 만나면 ROUTING.md의 절차로 정한다.

## 2. 응답값이 있어야 다음을 할 수 있는가

| 상황 | 선택 | 이유 | 근거 | 확인한 날 |
|---|---|---|---|---|
| 부른 쪽이 그 응답값으로 바로 다음 일을 한다 | 동기 호출. 3절로 간다 | 기다려야 하는 일이다 | 사용자 판단 2026-11-20 | 2026-11-20 |
| "일어났다"를 알리기만 하면 된다. 같은 프로세스, 같은 트랜잭션 | 인메모리 이벤트 | 가볍고, 통신 계층만 나중에 바꿀 수 있다 | 사용자 판단 (Hybrid-Event-Driven-Architecture `README.md:34-43`) | 2026-11-20 |
| "일어났다"를 알리기만 하면 된다. 다른 시스템, 다른 트랜잭션 | 메시지: Outbox + 메시지 브로커 + Inbox | DB와 브로커에 따로 쓰다 한쪽만 되는 일을 막고, 받는 쪽의 장애가 보내는 쪽으로 번지지 않는다 | 사용자 판단 (같은 곳) · 재 본 적 없음 | 2026-11-20 |

## 3. 누가 부르는가 (동기 호출)

| 상황 | 선택 | 이유 | 근거 | 확인한 날 |
|---|---|---|---|---|
| 내부 서비스가 내부 서비스를 부른다 | gRPC 단건 호출 | 내부 통신의 기본값. 스키마가 계약이 된다 | 사용자 판단 2026-11-20 (http-grpc-lab `README.md:597-603`) | 2026-11-20 |
| 브라우저나 외부 시스템이 부른다 | HTTP + JSON | 브라우저와 외부는 gRPC를 바로 부르기 어렵다 | 사용자 판단 2026-11-20 · 일반 지식 | 2026-11-20 |
| 관리자 화면이나 대시보드가 부른다 | HTTP + JSON | 개발과 확인이 쉽다 | 사용자 판단 (같은 README) | 2026-11-20 |

참고: 응답이 1~100KB이고 동시 사용자가 10명일 때 gRPC 단건이 HTTP 바이너리보다 30~67% 빨랐다 — 실측(다시 재는 중, `docs/phase/PHASE4_RESULT.md:52-77`). 같은 조건의 다른 회차에서는 HTTP가 앞섰다. 이 수치만으로 방식을 바꾸지 않는다.

## 4. 무엇을 보내는가

3절의 선택보다 이 절이 앞선다.

| 상황 | 선택 | 이유 | 근거 | 확인한 날 |
|---|---|---|---|---|
| 파일처럼 수백 KB가 넘는 바이트 덩어리 | HTTP로 바이트를 그대로 보낸다 (내부 서비스 사이라도) | 200KB에서 gRPC보다 14%, 1MB에서 2.1배 빨랐다 | 실측(다시 재는 중, `PHASE1_RESULT.md:37-42`, `PHASE4_RESULT.md:79-95`) | 2026-11-20 |
| 바이너리를 JSON에 넣어야 할 것 같다 | Base64로 JSON에 넣지 않는다. 바이트로 따로 보낸다 | 10KB 대비 500KB에서 처리량이 67% 줄었다 | 실측(다시 재는 중, `PHASE4_RESULT.md:52-95`) | 2026-11-20 |
| 서버가 계속 밀어 줘야 한다, 양쪽이 주고받아야 한다 | 내부 서비스 사이는 gRPC 스트림. 브라우저가 받는 쪽이면 아직 줄이 없다 | 기능이 필요해서 쓰는 것이다 | 사용자 판단 (같은 README "실시간 알림") · 스트림이 쓰일 조건에서 재 본 적 없음 | 2026-11-20 |
| 큰 응답 하나를 받는다 | 스트림으로 나눠 받지 않는다 | 1MB 단일 응답에서 스트림이 가장 느렸다(211 req/s, HTTP 바이트 2,506) | 실측(다시 재는 중, `PHASE1_RESULT.md:37-42`) | 2026-11-20 |

## 규칙으로 쓰지 않는 것

아래는 실험 README의 가이드에 있지만 근거가 약해 줄로 넣지 않았다. 다시 잰 뒤에 정한다.

- "필드가 150개 이상이면 HTTP가 낫다": 그 구간의 HTTP 경로는 응답을 풀지 않고 바이트로만 받았다. 같은 조건의 비교가 아니다.
- "동시 사용자가 200명 이상이면 gRPC가 낫다": 1회 실행이고 차이(9~12%)가 반복 편차보다 작다.
- 복잡한 데이터에서의 gRPC 스트림 수치: 단건과 같은 코드를 잰 값이다.

## 아직 줄이 없는 것

타임아웃과 재시도, 장애가 번지는 것을 막는 방법 · 인스턴스가 여러 개일 때의 부하 분산(gRPC의 긴 연결) · 스키마를 바꿀 때의 호환 · 서비스 사이에 네트워크 지연이 있을 때의 선택 · 브라우저로 계속 밀어 주는 방식(SSE, WebSocket). 만나면 ROUTING.md의 절차로 정한다.
