# playbook: 작업을 task로 나누고 task마다 한 바퀴

> 트리거: 명세서를 쓸 때(9절 task 분해), 그리고 합의 뒤 task를 진행할 때.
> 왜: 인터뷰와 합의는 앞에서 한 번이면 되지만, 구현·검증·리뷰를 전부 모아 한 번에 하면 리뷰어도 사용자도 한꺼번에 봐야 할 양이 커진다(2026-11-19 v4.5: task 여섯을 한 명세에 적고 전체 diff를 리뷰해 3회가 돎. 2026-11-20: 작게 자른 작업 네 건은 건마다 리뷰 1회, 20분~1시간). 나누는 기준을 정하고, task마다 한 바퀴를 돌린다. 근거와 대어 본 결과: `docs/plans/2026-11-20/task-units/`. 규칙을 정하는 task(§2): `docs/plans/2026-11-22/service-communication-http-default/` task 07.

## 1. 언제, 어디서 나누나
- **결과를 한 문장으로 말할 수 없는 작업은 강도와 상관없이 나눈다.** 뭉뚱그린 문장("가입 기능을 만든다")은 한 문장이 아니다 — 끝났을 때 참인 것을 적었을 때 한 문장인지를 본다.
- **task 하나 = 결과를 한 문장으로 말할 수 있고, 그 결과가 함께 확인되는 변경.** 한 문장으로 되더라도 아래 신호 가운데 하나라도 해당하면 그 자리에서 자른다.

| 자르는 신호 | 예 |
|---|---|
| 목표 문장이 "그리고"로 이어진다 | 폴더를 지우고, 훅도 지운다 |
| 성격이 다르다 (새 동작, 동작은 그대로인 구조 변경(리팩토링), 삭제, 스키마·데이터 이관, 설정, 문서) | 판정 규칙을 조이는 것과 알림을 새로 더하는 것 |
| 서로 없이도 성립한다 | 한쪽만 들어가도 쓸 수 있다 |
| 확인하는 방법이 다르다 | 테스트로 확인되는 것과 실제 세션에서만 확인되는 것 |
| 틀렸을 때 아픈 정도가 다르다 | 문서 한 줄과 쓰기를 막는 훅 |
| 되돌리는 단위가 다르다 | 저장소 안의 변경과 `~/.claude` 설정 변경 |

**자르지 않는 경우(위 신호보다 앞선다)**: 하나만 들어가면 틀린 상태로 남는 변경은 한 task다(훅을 지우는 것과 그 등록을 지우는 것, 컬럼 형식을 바꾸는 것과 기존 데이터를 옮기는 것, 규칙을 바꾸는 것과 그 규칙을 확인하는 테스트). 자른 결과 task가 다른 task 없이는 확인될 수 없으면 너무 잘게 자른 것이다.

**순서**: 뒤의 task가 기대는 것을 먼저 둔다(이것이 앞선다). 서로 기대지 않는 task 사이에서는 되돌리기 어려운 것, 강도가 높은 것을 뒤에 두어 가벼운 task가 먼저 검증받고 커밋되게 한다.

## 2. 명세에 task마다 적는 것
| 칸 | 내용 |
|---|---|
| 결과 | 한 문장. 끝났을 때 무엇이 참인가(확인할 수 있는 말로) |
| 끝났을 때의 모습 | 그 결과가 어디에 어떤 꼴로 있나 — 생기거나 바뀌는 파일, 화면, 응답의 예(사용자가 미리 그려 볼 수 있게). 결과를 되풀이하지 않는다 |
| 다음 task에 주는 영향 | 이 task의 결과 위에 다음 task가 무엇을 얹나. 여기서 정해지면 뒤에서 못 바꾸는 것. 기대는 task가 없으면 "없음" |
| 분기 | 사용자가 골라야 하는 갈림. 선택지마다 그 결과를 한 줄로, 권장을 표시 |
| 검증 | 이 task를 무엇으로 확인하나 |
| 강도 | 이 task의 stakes(core §3). 작업 전체가 아니라 task마다 매긴다 |

- **분기는 합의 때 한꺼번에 묻는다.** 모든 task의 분기를 모아 질문하고, 받은 답을 명세의 "분기의 답" 표에 시각과 함께 적어 고정한다. 그 뒤에는 그 답대로 진행한다.
- 앞의 task를 해 봐야 답할 수 있는 분기는 지어내지 않는다. "task N이 끝난 뒤 묻는다"고 적고 그때 묻는다. task가 하나뿐이고 분기가 없으면 여섯 칸을 한 줄씩으로 줄여 적는다.
- 분기에 올릴 것: 어느 쪽을 고르느냐에 따라 사용자가 받는 결과가 달라지는 갈림(실패하면 어떻게 되나, 맞지 않는 데이터를 어떻게 하나, 어디까지 하나), 그리고 나중에 바꾸기 비싼 갈림(저장 형식, 공개되는 모양). 메인이 근거를 대고 정할 수 있고 나중에 바꾸기 쉬운 것(어느 파일에 둘지, 이름, 내부 구현 방식)은 분기가 아니다 — 진행 중 결정으로 기록한다(§4).
- 다른 문서나 작업이 따를 규칙을 정하는 task는, 합의를 받기 전에 정하려는 규칙 문장을 실제 사례 두세 개에 대어 본 결과를 사용자에게 함께 보인다. 사례는 규칙이 잘 들어맞는 것과 들어맞지 않아 보이는 것을 섞어 고른다.

## 3. task마다 한 바퀴
```text
task N: 구현 -> 커밋 -> 검증(이 task의 강도대로) -> 지적 가르기 -> 고친 것 커밋   (task마다 되풀이)
마지막 확인(전체 diff, task 사이의 어긋남만) -> 진행 중 결정을 사용자에게 확인 -> 마감
```

- **검증은 task마다 그 task의 강도대로 한다**(core §4 강도표 — 낮음은 셀프체크, 중간은 듀얼 1패스, 높음은 듀얼 리뷰 루프). 강도가 다른 task를 한 리뷰에 묶지 않는다.
- **리뷰 대상은 그 task의 diff다.** 리뷰 묶음(`review.md` §1 ⓪)의 base는 그 task를 시작할 때의 커밋이고, 리뷰어에게 주는 명세는 전체 명세이되 명세의 task 번호로 "이번에 볼 task"를 지목한다.
- **지적은 `review-triage.md`로 가르고, ledger에 task 번호를 함께 적는다**(루프 번호는 task마다 따로 센다).
  - (4)의 "목표나 불변식"은 그 task의 결과 문장과 작업 전체의 불변식이다.
  - 명세가 다른 task에 배정한 일을 "빠졌다"고 한 지적은 (1)의 "전에 판정함"이다 — 기각하고 근거에 그 task 번호를 적는다. 대칭 부담의 렌즈에서도 그런 것은 해당 없음으로 판정한다.
  - **같은 작업의 앞 task가 만든 결함은 "원래 있던 것"이 아니다.** 이 작업이 만든 것이므로 (3)에서 걸러지지 않는다. 지금 task에서 가장 작은 변경으로 막을 수 있으면 여기서 고치고, 앞 task의 결과를 고쳐야 하면 그 task를 다시 열어 고친 뒤 고친 곳만 그 task의 강도로 다시 확인한다.
  - 후보 가운데 "목표에 필요"한 것을 이 작업의 task로 더하려면 사용자에게 묻는다(합의에 없던 task다). 묻지 않으면 종전대로 마감 때 다음 작업으로 제안한다.
- **채택된 지적을 고치기 전에는 다음 task로 가지 않고, 마감하지도 않는다.** 리뷰가 끝나지 않으면(`review unresolved`) 멈추고 사용자에게 묻는다 — 보류하고 다음 task로 갈지는 사용자가 정한다.
- **마지막 확인**은 리뷰를 다시 하는 것이 아니다. 전체 diff에서 다음만 본다: 한 task가 바꾼 것을 다른 task가 옛 모습으로 쓰고 있지 않은가 · 문서와 코드, 문서와 문서가 서로 맞는가 · 작업 전체의 목표와 불변식이 지켜졌는가 · 전체 테스트가 통과하는가. 메인이 하고, 높음인 task가 하나라도 있었으면 다른 모델에게 한 번 보인다(주는 것과 맥락 차단은 `review.md` §1 ⓪·①과 같고 base만 작업 시작 커밋). 여기서 나온 지적도 `review-triage.md`로 가르고 ledger의 task 칸에 "마지막"이라고 적는다. 채택된 것은 그것을 만든 task의 강도로, 고친 곳만 다시 확인한다.

## 4. 진행 중 결정
합의 뒤에 생긴 결정은 하나씩 아래에 대어 본다. 넷 가운데 하나라도 해당하면 **멈추고 묻는다.**

| 멈추고 묻는 것 | 예 |
|---|---|
| 뒤의 task가 이 결정 위에 쌓인다 | 저장 형식, 공개되는 이름, 뒤 task가 읽을 값의 뜻. 명세의 "다음 task에 주는 영향"에 이미 적힌 것은 합의된 것이라 묻지 않는다 |
| 합의한 것을 바꾼다 | 분기의 답, 목표, 불변식, 금지영역, 사용자가 대화에서 정한 규칙. 완화하는 쪽이든 덧붙이는 쪽이든 |
| 되돌릴 수 없다 | 삭제, 이미 쌓인 데이터의 변경, 저장소 밖의 설정(`~/.claude` 등) 가운데 명세에 없던 것 |
| 허가 범위 밖으로 나간다 | §5에서 고른 범위에 없는 push, PR, 병합, 다른 저장소 |

- **그 밖은 기록하고 진행한다.** 작업 log의 "진행 중 결정" 표에 시각, task, 결정, 왜 묻지 않았나, 뒤 task가 기대나를 적는다. 예: 어느 파일에 둘지, 리뷰 반영으로 고칠 곳이 늘어난 것(목표와 불변식은 그대로), 검증을 더 한 것.
- 목표와 불변식은 그대로인 채 고칠 곳만 느는 것은 기록하고 진행한다. 명세의 불변식 문장을 고쳐야 진행할 수 있으면 합의한 것을 바꾸는 것이다. 넷에 해당하는지 망설여지면 묻는다. 묻는 쪽의 비용은 한 번 멈추는 것이고, 묻지 않은 쪽의 비용은 그 위에 쌓인 task 전부다.
- **마감 때 표를 사용자에게 보여 확인받는다.** 사용자가 바꾸라고 한 결정은 그것을 내린 task를 다시 열어 고친다(§3의 앞 task를 다시 여는 방식).

## 5. 커밋과 push의 허가 범위
합의 질문에 허가 범위를 함께 묻고, 답을 명세 7절에 적는다. 그 범위 안에서는 다시 묻지 않는다.

| 고르는 범위 | 묻지 않고 하는 것 | 여전히 묻는 것 |
|---|---|---|
| 매번 묻기 | task마다 커밋 | push, PR 생성, 병합 |
| 브랜치의 커밋·push·PR 생성까지 | task마다 커밋, 작업 브랜치 push, 그 브랜치의 PR 생성 | 병합 |
| 병합까지 | 위의 것과 그 PR의 병합 | 없음(마지막 확인은 병합 뒤에 보고) |

- **어느 범위에도 들지 않는 것**(늘 그때 묻는다): 강제 push, `main`에 직접 push, 브랜치나 파일의 삭제, 명세에 없던 다른 저장소, 이슈 생성과 코멘트, 릴리스.
- 범위는 그 작업에만 쓴다. 다음 작업에서 다시 고른다. 병합 전에 마지막 확인(§3)과 진행 중 결정의 확인(§4)을 마친다. "병합까지"를 골랐더라도 넷 가운데 "멈추고 묻는 것"이 남아 있으면 병합하지 않는다.
- 이 범위는 메인이 질문하지 않는다는 절차다. `git-guard` 훅은 그대로라서, Claude Code가 push에 승인 창을 띄우는 환경에서는 그 창이 계속 뜬다(훅이 범위를 읽게 하는 것은 따로 정한다).
