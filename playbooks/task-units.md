# playbook: 작업을 task로 나누고 task마다 한 바퀴

> 트리거: 명세서를 쓸 때(9절 task 분해), 그리고 합의 뒤 task를 진행할 때.
> 왜: 인터뷰와 합의는 앞에서 한 번이면 되지만, 구현·검증·리뷰를 전부 모아 한 번에 하면 리뷰어도 사용자도 한꺼번에 봐야 할 양이 커진다(2026-11-19 v4.5: task 여섯을 한 명세에 적고 전체 diff를 리뷰해 3회가 돎. 2026-11-20: 작게 자른 작업 네 건은 건마다 리뷰 1회, 20분~1시간). 나누는 기준을 정하고, task마다 한 바퀴를 돌린다.
> 근거와 대어 본 결과: `docs/plans/2026-11-20/task-units/`.

## 1. 언제, 어디서 나누나

- **결과를 한 문장으로 말할 수 없는 작업은 강도와 상관없이 나눈다.** 한 문장으로 되면 task 하나다.
- **task 하나 = 결과를 한 문장으로 말할 수 있고, 한 가지 방법으로 확인되는 변경.**

아래 가운데 하나라도 해당하면 그 자리에서 자른다.

| 자르는 신호 | 예 |
|---|---|
| 목표 문장이 "그리고"로 이어진다 | 폴더를 지우고, 훅도 지운다 |
| 성격이 다르다 (새 동작, 구조 변경, 삭제, 설정, 문서) | 판정 규칙을 조이는 것과 알림을 새로 더하는 것 |
| 서로 없이도 성립한다 | 한쪽만 들어가도 쓸 수 있다 |
| 확인하는 방법이 다르다 | 테스트로 확인되는 것과 실제 세션에서만 확인되는 것 |
| 틀렸을 때 아픈 정도가 다르다 | 문서 한 줄과 쓰기를 막는 훅 |
| 되돌리는 단위가 다르다 | 저장소 안의 변경과 `~/.claude` 설정 변경 |

**자르지 않는 경우**: 하나만 들어가면 틀린 상태로 남는 변경은 한 task다(훅을 지우는 것과 그 등록을 지우는 것, 규칙을 바꾸는 것과 그 규칙을 확인하는 테스트). 자른 결과 task가 다른 task 없이는 확인될 수 없으면 너무 잘게 자른 것이다.

**순서**: 뒤의 task가 기대는 것을 먼저 둔다. 되돌리기 어려운 것, 강도가 높은 것은 뒤에 두어 앞의 task가 먼저 쓰이게 한다.

## 2. 명세에 task마다 적는 것

| 칸 | 내용 |
|---|---|
| 결과 | 한 문장. 끝났을 때 무엇이 참인가 |
| 끝났을 때의 모습 | 어떤 파일과 동작이 어떻게 되어 있나(사용자가 미리 그려 볼 수 있게) |
| 다음 task에 주는 영향 | 이 task의 결과 위에 다음 task가 무엇을 얹나. 여기서 정해지면 뒤에서 못 바꾸는 것 |
| 분기 | 사용자가 골라야 하는 갈림. 선택지마다 그 결과를 한 줄로, 권장을 표시 |
| 검증 | 이 task를 무엇으로 확인하나 |
| 강도 | 이 task의 stakes(core §3). 작업 전체가 아니라 task마다 매긴다 |

- **분기는 합의 때 한꺼번에 묻는다.** 모든 task의 분기를 모아 질문하고, 받은 답을 명세의 "분기의 답" 표에 시각과 함께 적어 고정한다. 그 뒤에는 그 답대로 진행한다.
- 앞의 task를 해 봐야 답할 수 있는 분기는 지어내지 않는다. "task N이 끝난 뒤 묻는다"고 적고 그때 묻는다.
- 분기에 올릴 것은 사용자의 선택이 결과를 바꾸는 갈림이다. 메인이 정해도 되는 구현 선택(어느 파일에 둘지, 이름)은 분기가 아니다.
