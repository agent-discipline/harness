## 1. 목표·대상 (필수)

하네스(`agent-discipline/harness`)에서, **중간 이상 stakes 작업의 구현(코드·테스트·배포 구성 작성)은 Opus 워커가 하고 메인은 PM 역할만 한다**는 것이 규칙 문면과 훅 알림 양쪽에서 드러나게 한다. 테스트 설계는 중간부터 구현자와 다른 워커가 명세에서 출발해 쓴다.

## 2. 경계·불변식 (필수)

- **구현 주체(문서 규칙)**: stakes 중간·높음 → **L1 전체(core §1 의 정의 — 코드·테스트·스크립트·설정·스키마·배포 구성 + 실행 정책 파일)** 의 작성·수정은 Opus 워커가 한다(11-22 사용자 결정 "정책 파일도 워커가" — 처음 문면은 실행 정책 파일을 빼고 나열했다. DB·데이터를 직접 바꾸는 조작은 아래 ③ 사용자 확인이 필요한 조작이다). 테스트를 쓰는 워커와 리뷰 지적을 고치는 워커도 구현 워커다 — 회수 규칙이 똑같이 적용된다. 메인은 직접 쓰지 않는다. 메인이 직접 해도 되는 것: ①낮은 stakes 작업 ②긴급 수정 ③사용자 확인이 필요한 조작(서버·DB 조작, 발행 — 원래 메인 소유) ④docs/** 기록 ⑤**lazy 모드의 작업**(매 diff 를 메인이 쓰고 설명하고 사용자가 이해를 확인한다 — `implementation-lazymode.md`. 11-21 리뷰 루프 1 에서 드러난 빈칸, 사용자 결정 "lazy는 메인이 직접"). 메인 소유(인터뷰·명세·task 분해·브리핑·게이트 판정·종합·log)는 그대로다.
- **테스트 설계(문서 규칙)**: 낮음 = 구현자 / **중간 = 구현자와 다른 워커가 명세에서 출발해 작성** / 높음 = 현행 그대로(별도 워커 + 구현 diff 미열람 계약). 테스트가 구현 결함을 드러내면 테스트를 구현에 맞추지 않고 구현을 고친다.
- **워커 결과 회수(문서 규칙)**: 메인은 ①워커가 보고한 테스트를 직접 다시 돌려 통과·실패·**건너뜀** 수를 센다(건너뜀 ≠ 통과) ②보고와 실제 diff 범위를 대조한다(범위 밖 파일, 커밋 메시지 규칙) ③같은 저장소에 워커를 동시에 넣을 때는 파일 범위를 나누고, 모두 끝난 **마지막 상태에서** 빌드·테스트를 다시 확인한다. 탐색(explorer) 결과의 "핵심 1~2개 교차 확인"은 그대로다.
- **리뷰에서의 역할(문서 규칙 — 11-21 사용자 추가)**: `src/core.md` 에 한 줄로 못 박는다 — **리뷰어(Opus 워커 ∥ codex)는 결함을 찾고, 메인은 그 지적을 명세에 비추어 판정한다**(기각 / 지금 고친다 / 후보). 메인은 리뷰어가 아니다. 지금 `playbooks/review.md` 가 정한 절차를 그대로 요약한 문장이며 절차는 바꾸지 않는다(`review.md` 는 고치지 않는다).
- **품질 우선(문서 규칙)**: 워커 위임의 목적은 품질(생성과 검증의 분리)과 메인 컨텍스트 보호다. 토큰 비용이 늘어나는 것은 받아들인다 — 비용을 이유로 중간 이상에서 메인이 직접 구현하지 않는다. §0.2 의 "컨텍스트 비용은 1급 제약"은 **상시 주입 문서의 크기**에 대한 원칙임을 분명히 한다(워커 사용을 줄이라는 뜻이 아니다).
- **훅 알림(새 동작 불변식)**: `gate-guard` 가 **메인**(훅 입력에 `agent_id` 없음)의 Edit/Write 를 L1 경로로 판정하고 통과시킬 때(SPEC=1·MODE=auto), "구현은 Opus 워커에게(낮은 stakes·긴급 제외) — core §5" 한 줄을 알린다. **막지 않는다**(종료 코드·차단 판정은 지금과 같다). 알림은 **작업 폴더(TASK_PATH)마다 한 번**만 낸다. 다음 경우에는 내지 않는다: 워커의 쓰기(`agent_id` 있음) · docs/** 등 L0 경로 · lazy 모드 · 이미 차단되는 경우(차단 사유만 낸다) · 긴급(DEBT=1 로 들어온 작업). Bash 로 쓰는 경우는 지금처럼 판별하지 않는다(절차 규칙).
- **훅 알림의 세부(11-21 설계 선검증 반영 — 위 조항의 뜻을 확정한다)**:
  - 대상 도구: `gate-guard` 가 같은 경로로 처리하는 Edit·Write·MultiEdit 의 **PreToolUse**. PostToolUse 와 Bash 에는 내지 않는다.
  - 메인 판별: 기존 훅과 같은 기준 — `agent_id` 가 없거나 비어 있으면(빈 문자열·null) 메인.
  - "L1 경로": `gate-guard` 의 기존 분류를 그대로 쓴다(저장소 안의 비-docs 파일과 정책 파일). 훅이 L0 으로 통과시키는 경로에는 내지 않는다.
  - "낮은 stakes·긴급 제외"는 **알림 문장 안의 안내**다. 훅은 stakes 를 알 수 없으므로 낮은 stakes 작업에서도 한 번은 뜬다. 긴급은 `DEBT=1` 로 판별해 내지 않는다.
  - "한 번"의 범위: **세션마다, 작업 폴더(TASK_PATH)마다 한 번.** 다른 세션에서는 같은 폴더여도 다시 한 번 낸다(새 세션의 메인은 그 알림을 본 적이 없다). TASK_PATH 가 비어 있으면 "폴더 없음"을 하나의 폴더로 센다. 압축은 세션을 끝내지 않으므로 다시 내지 않는다.
  - 출력: 통과(exit 0)와 함께 stdout 에 `{"hookSpecificOutput":{"hookEventName":"PreToolUse","additionalContext":"…"}}` 한 덩어리만. 다른 JSON(고정 지시 파일의 `ask`)을 내는 경로와 차단 경로에는 내지 않는다 — 한 호출의 stdout 에 JSON 이 둘 이어 붙지 않는다.
  - 판정 순서: 기존 차단·통과 판정이 **모두 끝난 뒤**, 통과가 확정된 경우에만 낸다.
  - 기억하는 곳: 세션 상태 디렉토리의 사이드카 파일(상태파일·SCHEMA=4·set-state 키는 건드리지 않는다. 상태 디렉토리의 기존 보호 — 심링크·gitignore·잠금 규약 — 을 우회하지 않는다). 동시에 들어온 두 호출 중 하나만 낸다("이미 냈나 확인 → 기록"이 한 잠금 안).
  - 실패 정책: **통과가 우선.** 사이드카 기록·잠금·JSON 생성이 실패하면 알림을 내지 않고 조용히 통과시킨다 — 알림 때문에 기존에 통과하던 쓰기가 막히거나 비정상 종료하는 일이 없어야 한다. 여기서 "조용히"는 **모델에게 보이는 출력(stdout)이 없다**는 뜻이다 — 실패 사실은 stderr 한 줄로 남긴다(실패를 드러내기, core §4. 통과 시 stderr 는 모델에게 보이지 않으므로 판정에 영향이 없다). 실패한 호출은 "한 번"을 소비하지 않는다. **실패 방향(11-22 사용자 결정 — 리뷰 루프 2 뒤 재설계)**: 알림이 **빠지는 일은 없게** 하고, 드물게 한 번 더 뜨는 것은 받아들인다. 순서는 ①기록할 내용 준비(임시 파일) → ②알림 출력 → ③기록 확정(이름 바꾸기)이고 셋 다 한 잠금 안이다. ①·②가 실패하면 ③을 하지 않는다 — 사이드카는 바이트까지 그대로다(다른 작업 폴더의 기록도 그대로, 되돌리기 단계가 없다). ②는 됐는데 ③만 실패하면 알림은 이미 나갔고 기록이 없으므로 다음 호출에서 한 번 더 뜬다(stderr 한 줄로 남긴다). "빠지지 않는다"의 뜻: 잠금 대기 실패 등으로 한 호출에서 알림이 생략될 수는 있다 — 그 호출은 한 번을 소비하지 않으므로 같은 폴더의 다음 쓰기에서 뜬다(영영 안 뜨는 경로가 없다는 뜻이다). 출력 대상이 닫혀 있어도(SIGPIPE) 훅은 죽지 않고 통과한다 — stdout 과 stderr 가 함께 끊겨도 같다. **출력 실패의 보장 범위(11-22 리뷰 루프 3 — 실측)**: 알림 JSON 은 한 번의 write(2)로 나가고(실측 313바이트) PIPE_BUF(4096)보다 짧게 유지한다 — 파이프로 받는 stdout(Claude Code 의 훅 실행)에서는 전부 나가거나 전혀 나가지 않는다. 파이프가 아닌 stdout(파일로 돌린 경우의 디스크 풀 등)에서 일부만 쓰이는 경우는 보장 범위 밖이다 — 이미 나간 바이트는 어떤 순서로도 되돌릴 수 없다(그때도 기록은 확정하지 않는다). stderr 경고는 실패한 단계를 구분해 적는다(잠금 / 준비 / 출력 / 확정). 정상 경로에서는 stderr 에 아무것도 더하지 않는다(기존 출력과 바이트까지 같다).
- **불변(바꾸지 않는 것)**: SPEC/MODE 게이트의 차단 판정 · 상태파일 스키마(SCHEMA=4)와 set-state 의 키 · lazy 모드의 동작 · 리뷰 강도표의 리뷰 행 · 측정 로그의 열 수(13열) · 배포 절차.
- **문서 정합**: 강도표는 `src/core.md` 와 `README.md` 두 곳에 있다 — 같은 내용이어야 한다. `playbooks/task-units.md` 는 80줄 상한 안에 머문다(지금 79줄).
