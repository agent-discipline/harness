## 3. 기록에서 찾은 다른 원인

1. **요구의 표를 걸러진 출력으로 읽었다**(4 의 직접 원인). `grep … | head -8`(01:55) · `grep … | grep -n "llm\|alert\|observe"`(03:03). core §4 의 "그린 위장 점검"은 테스트 출력의 `| tail` 류를 찾게 하지만 **요구 문서를 읽는 출력**의 절단은 어디에도 적혀 있지 않다. silent failure(조용한 절단)의 한 꼴이다.
2. **닫힌 task 의 빠짐을 알고도 다시 열지 않고 후보로 내렸다**(2 → 3). task-units §3 49행 "앞 task의 결과를 고쳐야 하면 그 task를 다시 열어 고친다"는 리뷰 지적을 가를 때의 규칙이고, 탐색(explorer) 보고에서 나온 빠짐에는 걸리지 않았다. 명세 §8 의 T5 는 "앞선 것: T4"였다 — 앞선 것이 다 되지 않은 채 T5 를 시작했다.
3. **명세의 task 표와 계약 문서의 표가 서로 다른 범위를 가졌다**. 명세 §8: T2 = front · backend · llm, T9 = backend · observe · admin. 규약 §7.1: T2 = 일곱, T9 = backend · llm · observe · ci-cd. 규약 3행은 "명세와 다르면 명세가 앞선다". 메인은 착수 때 규약 쪽을 썼다(log 45행 "규약 7.1"). 어느 표가 정본인지가 task 마다 갈렸다.
4. **뒤 task 로 넘어가야 할 몫이 넘어가지 않았다**(5). T8(admin)의 한 줄이 T5(ci-cd 에이전트 — 뒤에 만든 것)의 표를 바꾸는 일이었다. task-units §2 의 "다음 task에 주는 영향" 칸은 "이 task 위에 다음 task가 얹는 것"을 적게 하지만, "이 task 의 요구 가운데 다른 task 가 해야 하는 것"을 넘기는 칸은 없다.
5. **리뷰의 범위는 구조상 "만든 것"이다**. task-units §3 45행 "리뷰 대상은 그 task의 diff다" · review.md ⓪′ "spec과 일치하는가로 판정" — 리뷰어는 spec 을 받지만 diff 가 없는 저장소는 볼 곳이 없고, 브리핑의 "정한 것(다시 내지 않는다)"이 넘김을 닫았다(1.2 ⑤).
6. (원인인지는 기록으로 알 수 없다) **같은 세션이 여러 묶음을 동시에 돌렸다**: 11-25 16:00 ~ 11-26 04:00 의 메인 워커 호출에 ⑤ ⑥ ⑧ ⑨ ⑩ ⑪ ⑫ ⑬ 여덟 묶음이 섞여 있다. 또 그 사이 메인이 `playbooks/` 아래 문서를 Read · cat · sed 로 연 기록은 0건이다(11-25 13:00 이후) — 조건부 문서는 이 기간 메인의 맥락에 새로 들어오지 않았다.
