## 1. 목표·대상 (필수)

하네스에서, 한 작업을 task 단위로 나누고 **구현·테스트·리뷰가 task마다 돌게** 한다. 인터뷰와 합의는 종전대로 앞에서 한 번이다. 진행 중에 멈추는 횟수를 줄이되, 뒤의 task가 기대는 결정은 멈추고 묻는다.

## 2. 경계·불변식 (필수)

- **I1 앞단은 한 번**: 인터뷰, 명세, 합의, 자율성 선택은 작업마다 한 번이다. 게이트(SPEC·MODE)의 동작은 바꾸지 않는다.
- **I2 task의 형식**: 명세의 task마다 ①결과 한 문장 ②끝났을 때의 모습 ③다음 task에 주는 영향 ④분기(선택지와 각각의 결과, 권장) ⑤검증 방법 ⑥강도를 적는다. 분기의 답은 합의 때 한꺼번에 받아 명세에 적는다.
- **I3 task마다 한 바퀴**: 각 task는 구현 → 검증(그 task의 강도대로) → 커밋을 마친 뒤 다음 task로 간다. 리뷰 대상은 그 task의 diff다.
- **I4 마지막 확인**: 모든 task가 끝나면 전체 diff에 대해 task 사이의 어긋남만 보는 확인을 한 번 하고, 진행 중 결정의 목록을 사용자에게 보여 확인받는다.
- **I5 진행 중 결정**: 합의 뒤에 생긴 결정은 종류에 따라 "멈추고 묻는다"와 "기록하고 진행한다"로 가른다(기준은 분기 C의 답). 기록하고 진행한 것은 작업 log의 "진행 중 결정" 표에 남긴다.
- **I6 커밋·push의 허가 범위**: 작업을 시작할 때 사용자가 고른다(분기 D의 답). 고른 범위 밖의 것은 종전대로 그때 묻는다. 강제 push, `main` 직접 push, 삭제는 어떤 범위에서도 전체 허가에 들지 않는다.
- **I7 상시 맥락**: `src/core.md`의 줄 수는 늘지 않는다(있는 줄을 고치거나 조건부 문서로 뺀다).
- **I8 기존 계약 보존**: 리뷰어의 독립성, finding 자격 조건, `review-triage.md`의 순서, 안전선 6항은 그대로다. 훅은 task 04에서 고르는 경우에만 고친다.

## 3. 기준소스 (필수)

## 4. 금지영역 (필수)

- 이번에 넣지 않는 것: 작업 유형별 의사결정 분기표, ERD를 키우는 기준, 3달마다 대안을 조사하는 구조(NEXT N11에 있음).

## 5. 검증 방법 (필수)

- task마다 9절에 적은 방법.
- 마지막: 이 작업 자체를 새 방식으로 진행한 기록(task마다의 커밋, 진행 중 결정 표, 멈춘 횟수)을 log에 남겨, 다음 작업에서 고칠 것을 후보로 적는다.

## 6. stakes (필수)

- 작업 전체가 아니라 task마다 매긴다(9절). task 01~03은 절차 문서와 양식이라 **중간**(대어 보기와 다른 모델의 읽기 1회 — `review-triage` 작업과 같은 방식), task 04는 분기 E의 답에 따라 **낮음**(문서만) 또는 **높음**(push 승인을 건너뛰게 하는 훅 변경).

## 9. task 분해

### task 01 — 나누는 기준과 명세의 task 형식

- **결과**: 작업을 어디서 자르는지의 기준과, task마다 적을 여섯 칸이 문서와 양식에 있다.
- **끝났을 때의 모습**: 새 문서 `playbooks/task-units.md`(나누는 신호, 나누지 않는 경우, task의 여섯 칸, 분기를 적는 법). `templates/requirement-spec.md` 9절이 새 형식. `src/core.md` 74행의 "최소 검증가능 증분"이 그 문서를 가리킴.
- **다음 task에 주는 영향**: task 02와 03은 이 문서에 절을 더한다. 문서의 이름과 절 구성이 여기서 정해진다.
- **분기 A — task 분해를 언제 의무로 하나**
  - A1(권장): 결과를 한 문장으로 말할 수 없는 작업이면 항상. 한 문장으로 되는 작업은 task 하나로 본다.
  - A2: 강도가 중간 이상인 작업만.
  - A1은 낮은 강도의 작업도 나누게 되어 명세가 길어질 수 있고, A2는 "낮음"으로 매긴 큰 작업이 빠져나간다.
- **검증**: 오늘 작업 다섯 건(정리, v4.6, v4.7, 리뷰 지적 가르기, 이 작업)을 기준에 대어, 기준이 가리키는 자르는 곳과 실제로 자른 곳을 비교한다. 다른 모델의 읽기 1회.
- **강도**: 중간.

### task 02 — 검증과 리뷰를 task 단위로

- **결과**: 리뷰 묶음이 task의 diff이고, 강도를 task마다 매기며, 마지막에 전체 확인이 한 번 있다.
- **끝났을 때의 모습**: `playbooks/review.md`의 묶음 설명이 "task 시작 커밋부터의 diff", core.md 강도표의 머리에 "task마다"가 들어감, `task-units.md`에 "마지막 확인" 절.
- **다음 task에 주는 영향**: task 03의 "진행 중 결정"이 마지막 확인에서 함께 검사된다.
- **분기 B — task마다 어떤 검증을 하나**
  - B1(권장): task마다 그 task의 강도대로 한다(낮음은 셀프체크, 중간은 듀얼 1패스 등). 모든 task가 끝난 뒤 전체 diff에 "task 사이의 어긋남"만 보는 확인을 한 번 한다.
  - B2: task마다 셀프체크만 하고, 리뷰는 마지막에 전체 diff로 한 번 한다(종전에 가까움).
  - B1은 task가 많으면 리뷰 횟수가 늘지만 한 번에 보는 양이 작다. B2는 횟수가 적지만 리뷰어가 전부를 한꺼번에 본다.
- **검증**: 다른 모델에게 가상의 task 셋을 주고 문서만 보고 "무엇을 언제 리뷰하나"를 답하게 한다.
- **강도**: 중간.

### task 03 — 진행 중 결정의 처리

- **결과**: 합의 뒤에 생긴 결정을 묻는 것과 기록하고 진행하는 것으로 가르는 기준이 있고, 기록한 것은 마감 때 확인받는다.
- **끝났을 때의 모습**: `task-units.md`에 "진행 중 결정" 절, `templates/log.md`에 "진행 중 결정" 표(이 작업의 log에 먼저 써 봄).
- **다음 task에 주는 영향**: task 04의 허가 범위는 "멈추고 묻는 것"의 한 종류다. 여기서 정한 가르는 기준 위에 얹는다.
- **분기 C — 무엇을 멈추고 묻나**
  - C1(권장): 다음 넷만 묻는다 — 뒤의 task가 기대는 결정, 합의한 분기의 답이나 목표·범위를 바꾸는 것, 되돌릴 수 없는 것, 밖으로 나가는 것(허가 범위 밖). 나머지는 기록하고 진행해 마감 때 한꺼번에 확인받는다.
  - C2: 전부 기록하고 진행한다. 마감 때 한꺼번에 확인받는다.
  - C3: 지금처럼 그때그때 묻는다.
  - C2는 멈추지 않지만, 뒤의 task가 기대는 결정이 틀렸을 때 마감에서야 드러나 뒤의 task를 다시 해야 한다.
- **검증**: 오늘 작업들에서 합의 뒤에 내린 결정을 모아 기준에 대어 본다(명세에 대상을 더한 것, 배포 순서를 바꾼 것, 규칙을 덧붙인 것 등).
- **강도**: 중간.

### task 04 — 커밋과 push의 허가 범위를 처음에 고르기

- **결과**: 작업을 시작할 때 사용자가 허가 범위를 고르고, 그 범위 안에서는 다시 묻지 않는다.
- **끝났을 때의 모습**: 합의 질문에 허가 범위가 들어가는 절차(`task-units.md`, core.md 6절의 push 줄). 분기 E가 E2면 여기에 더해 `set-state.sh`의 새 명령, 상태의 새 키, `git-guard.sh`의 판정, 그 테스트.
- **다음 task에 주는 영향**: 마지막 task다. E2를 고르면 이 task만 따로 높은 강도로 검증하고, 그 사이 task 01~03의 문서는 이미 배포돼 쓰이고 있다.
- **분기 D — 전체 허가를 줄 때의 범위**(작업마다 사용자가 고르는 선택지를 무엇으로 둘지)
  - D1(권장): 선택지 셋 — "매번 묻기" / "이 작업 브랜치의 커밋·push·PR 생성까지" / "병합까지".
  - D2: 선택지 둘 — "매번 묻기" / "이 작업 브랜치의 커밋·push까지"(PR과 병합은 늘 묻는다).
- **분기 E — 어떻게 강제하나**
  - E1(권장, 먼저): 절차로만 한다. 메인이 범위 안에서는 질문하지 않는다. 훅은 그대로라서, Claude Code가 push 때 승인 창을 띄우도록 설정된 환경에서는 그 창이 계속 뜬다.
  - E2: 훅이 상태를 읽어, 전체 허가를 받은 작업의 브랜치 push에는 승인 요청을 내지 않게 한다. 권한을 넓히는 훅 변경이라 강도 높음(듀얼 리뷰 루프, 구현을 보지 않는 테스트 설계)이고, 상태 형식이 바뀐다.
  - E1로 먼저 써 보고, 승인 창이 실제로 걸림돌이면 E2를 다음 작업으로 여는 순서를 권한다.
- **검증**: E1이면 이 작업의 마감에서 고른 범위대로 진행되는지 본다. E2면 훅 테스트와 실제 세션 확인.
- **강도**: E1이면 낮음, E2면 높음.
